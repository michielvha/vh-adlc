### R-2

FINDING: F-01
KIND: factual
SEVERITY: should-fix
WHERE: Design, Authority and delivery (publication lease); Scheduled worker and staged adoption; Test Plan AC-05, AC-06
EVIDENCE: The lease serializes "the scheduled worker and a local resolve publisher for the same consumer" (00081 line 80). Under the owner's staged choice, "Interactive adoption may precede that trial" (00081 line 14). The local scheduled worker stays active until the trial passes, and the spec says to "Preserve the existing worker bytes as a rollback target" (00161 lines 6, 8). It also says to "Do not change schedules" (00081 line 6). So the scheduled publisher running during the whole staged interval is the unchanged legacy worker, which never acquires the new lease. During that interval a shared local resolve run can push and close superseded proposals while the legacy worker publishes a new advisory PR, with nothing serializing them. delivery.md 00161 lines 8-9 requires serializing publication "where competing runs could conflict". The AC-05 lease race test only covers the shared scheduled and local publishers.
PROPOSAL: Define how the staged interval serializes publication. Options are: give the legacy worker a reviewed minimal lease acquisition as part of the routing migration; have shared resolve publication and closure detect an active or recent legacy run and refuse; or defer shared resolve publication until cutover. Add a race test for the legacy worker against a shared resolve publisher to AC-06.

Migration and rollback says "Use bounded synthetic source/docs/PR/feedback scenarios for actual model trials; do not resolve real drift PRs or publish real findings during acceptance" (00161 line 14). It also never says how the trial worker definition reaches a runnable unattended state, such as a dispatch-only workflow on the default branch, before the separate cutover change. FINDING: F-03
KIND: factual
SEVERITY: should-fix
WHERE: Design, Scan-result protocol and local correction; Entry and consumer contract; Test Plan AC-02
EVIDENCE: The design states "Missing required detector execution is a gap even if all document reads succeeded" (00081 line 38), and AC-02 tests "missing requested detectors" (00161 line 33). The v1 schema lists only declared "detector options", the document inventory, collection failures, findings, suppressed findings and stale suppressions (00081 line 36). It has no per-detector execution or outcome record. The consumer settings list scanner argv, scope, feedback files, procedure and commands, but no required detector set (00081 line 28). So the shared helper has no defined source for which detectors are required, and no observation proving they ran. A scanner that aborts or skips a detector after reading every document would still produce a complete inventory with fewer findings, which is the "lower finding count" case the spec forbids treating as proof (00081 line 32).
PROPOSAL: Add a required detector set to the committed settings, or derive it from the bound scanner options, and add a schema field recording each detector's execution outcome. Have the helper mark the result incomplete when a required detector is absent or failed, and require the Stackweaver correction to emit that field.

EVIDENCE: Context says `.claude/commands/docs-drift.md` selects the local resolver (00001 line 60). Scope says to preserve Stackweaver's current command "through thin forwarding instructions" (00081 line 6). Stage one adopts interactive preparation "while retaining all legacy real-corpus publishing routes" (00161 line 16). The spec never says whether the existing command forwards to the shared operation at stage one or only at cutover. If it forwards at stage one, it does not name the route an owner uses for the legacy resolver's push and superseded-PR closure. The AC-05 race tests cover shared against shared after cutover and shared against a legacy run before cutover, but not a legacy interactive resolver against the shared scheduled worker after cutover. That leaves the unserialized publication race from R-2 F-01 in the post-cutover state.
PROPOSAL: For each stage, state which entry point the existing command selects and which legacy resolve and closure route stays reachable. Require cutover to retire or disable every legacy real-corpus publication and closure route in the same reviewed change as `mode: adopted`, and require rollback to restore it. FINDING: F-02
KIND: factual
SEVERITY: should-fix
WHERE: Design, Independent candidate review and publication; Scheduled worker and staged adoption (trial); Test Plan AC-05, AC-06
EVIDENCE: The publication design allows "A final record-only commit ... when its diff contains evidence alone", made after the review, and says evidence goes into "the published artifact/PR through the authorized wrapper" (00081 line 80). The trial requires "The publisher pushes that same reviewed checkpoint without rewriting, transplanting, generating or remapping anything afterward; assert both published head and tree equal the reviewed consumer objects" (00161 line 20). It also requires "The candidate-review and publication steps themselves are unchanged" (00161 line 22). If the production publisher adds a record-only commit, either the trial's head-equality assertion fails or the trial publisher skips that step. Skipping it is a publisher difference that invalidates the trial under its own rule. The spec also never defines "evidence alone": which paths qualify, how the publisher checks that the post-review diff touches only those paths, and how the AC-05 "mismatched review" denial treats a head that differs only by that commit.
PROPOSAL: Choose one rule for both production and the trial. Either evidence goes only in the PR body or in an external artifact, and the published head always equals the reviewed commit. Or define an exact evidence path set that the publisher checks mechanically, and assert in the trial and in AC-05 that the reviewed commit is the parent and the only diff is within that path set.
FINDING: F-03
KIND: factual
SEVERITY: should-fix
WHERE: Design, Independent candidate review and publication; Authority and delivery (publication lease); Resolution and feedback; Test Plan AC-05
EVIDENCE: The review is invalidated by "Changed source/diff, settings, scanner/options/scope, feedback, selected PR heads/bodies or owner decision payloads" (00161 line 2). Under the lease, the publisher must "recheck the current base, PR selections and reviewed candidate before pushing or closing superseded proposals" (00161 line 10). For example, the publisher may proceed only when the current default commit has no changes since the reviewed base to the bound document scope, settings, scanner, feedback or generator inputs. Any such change means a fresh scan and review. Add AC-05 cases for an unrelated base advance and an in-scope base advance.

FINDING: F-06
KIND: factual
SEVERITY: nit
WHERE: Design, Scan-result protocol and local correction
EVIDENCE: The detector input digest "uses the existing stable-key `digest` primitive over source commit, settings/scope digests, feedback digests, detector ID/options and the sorted applicable `[path, content_sha256]` entries" (00081 line 42). ### R-5

FINDING: F-01
KIND: factual
SEVERITY: should-fix
WHERE: Design, Independent candidate review and publication (base freshness, publication gate); Scheduled worker and staged adoption (real unattended trial); Test Plan AC-05, AC-06
EVIDENCE: The trial assesses "a committed bounded synthetic documentation/code/feedback fixture in an isolated scratch Git repository" (00161 line 28). It then maps output "into an owned consumer branch based on the selected default commit" (line 30). The trial says "The candidate-review and publication steps themselves are unchanged" and treats any different "publisher behavior" as invalidating (line 32). The production freshness rule must "Bind the assessment to its exact base commit and input read set" and "read the current consumer default and compare its full delta from the assessed base". Under that rule, "A non-descendant base, unavailable comparison or any bound input change requires a fresh scan" (line 10). For the trial, the assessed base is a scratch-repository commit, so the consumer default cannot descend from it. Its read set also spans two repositories: fixture documents in scratch, and the scanner, worker and procedure in the consumer. An unchanged publisher would therefore always refuse the trial. Separately, staged configuration "denies shared real-corpus push, PR and closure effects" (line 12), but the spec never names the bound input the unchanged publisher uses to classify a run as the trial namespace rather than real corpus. The R-1 F-06 staged-cutover decision depends on this trial being passable without changing the publisher.
PROPOSAL: Define the trial's assessed base and read set for the publisher. For example, the freshness comparison uses the consumer base commit and the manifest's recorded scratch commit plus fixture digests. Name the committed trial-scope binding that lets the gate allow the trial namespace while it denies real-corpus effects. Add AC-06 tests showing the unchanged publisher accepts a valid trial and still refuses a trial-labelled run outside the namespace.
FINDING: F-02
KIND: factual
SEVERITY: should-fix
WHERE: Design, Independent candidate review and publication (publication gate); Scheduled worker and staged adoption (adoption evidence); Migration and rollback; Test Plan AC-06
EVIDENCE: The cutover commit sets `publication.mode: adopted`, and the publication block names "the committed adoption-record path/digest" (00161 lines 12, 16). The adoption helper validates that record's "passing trial, exact component and worker/reviewer/publisher bindings, paired acceptance and recorded cutover route" (line 14). Paired review "binds the exact installed shared payload and consumer candidate" (line 42). If the record is committed in the cutover change, it cannot contain the paired acceptance of the commit that contains it, because that commit's ID depends on the record bytes. Adoption evidence `adopted` also "requires a passing exact trial receipt, paired review and observed post-cutover worker route" (line 34). A post-cutover observation cannot exist in the record committed by the cutover itself. The first post-cutover scheduled run is also the publisher that needs the gate to pass. The spec does not say whether the gate requires evidence state `adopted` (which is circular) or accepts `trial-passed` plus a recorded route (which means publication runs before the state `adopted` describes).
PROPOSAL: Say exactly which consumer candidate the paired acceptance binds and how the committed record refers to it without self-reference. For example, bind the reviewed candidate tree minus the record path, or the parent commit with a mechanically checked record-only diff. State which evidence state the gate requires for the first post-cutover publication, and when and through which authorized change the observed post-cutover route is recorded.
FINDING: F-03
KIND: factual
SEVERITY: should-fix
WHERE: Design, Audit and preparation (feature-document protection); Test Plan AC-03

It would do this on its own drift branch without the one-writer handoff (delivery.md 00001 lines 75-77) and without reporting the resulting review staleness. AC-03 only tests the feature document itself.
PROPOSAL: State how prepare and resolve treat edits to paths covered by in-progress or complete features. At minimum, report the affected features and their implementation-review staleness, and require the claiming writer's handoff or explicit selection before editing a path covered by a claimed feature. Add an AC-03 case for a doc covered by an in-progress feature.
