# Plan: Offline SEO evidence workbench

Build a standalone Bun toolkit for saved crawl evidence, link graphs, duplicate-page checks and technical snapshot comparisons. Its files and verification workflow are separate from both active SEO feature scopes.

## Context

### Owner summary

The SEO agent already describes useful public checks and preserves evidence. Its maintained executable helper handles Semrush, not cross-page analysis or technical regression comparison. The proposed AI-discovery addition concerns provider access, measured visibility and repair routing; it does not supply this analysis engine. Repeating those checklists would add little. A small evidence toolkit would let us run the same checks reliably on saved crawls and test whether a site change broke something.

The research examined established open-source skills and tools at exact source revisions. The useful ideas are explicit technical baselines from Claude SEO, graph-based orphan and duplicate checks from SEOnaut, contextual link analysis from SEO Machine and the marketing skills, and explicit CI failure contracts and sampling coverage from SiteOne and Unlighthouse. These are design references. This feature neither installs their plugins nor adopts their entire checklists or rankings claims.

The owner selected saved-evidence analysis first, with live collection deferred. The toolkit will consume a documented local bundle, produce technical snapshots and findings, and compare two explicit snapshots. It will identify observed broken links, pages unreachable within the supplied graph, duplicate titles/descriptions/main content, and changes such as a new noindex directive or a removed title. Every result retains its evidence and coverage limits. An unseen target stays unobserved; an incomplete crawl does not prove a site has an orphan page. Template groups make coverage visible without treating a sampled page as proof about every page in its group.

The owner also selected report-only behavior by default, with CI failure enabled only for named rules in a repository policy, and final-document graph nodes with explicit recorded redirects. Captured responses need a known final URL; conflicting observations remain unverified. Invalid or incomplete inputs still return an unsuccessful execution status. There is no aggregate SEO score, keyword-density target or promise of better rankings. The first version makes no network requests, runs no browser and changes no site files, accounts or search-engine settings.

Implementation source owns only `tools/seo-evidence/` and a new `.github/workflows/seo-evidence.yml`; this feature document also receives its required lifecycle updates. It needs neither existing SEO feature to land and does not edit their agent, skill, manifests, tests, adapters or current workflow. A person or agent can invoke the documented command directly from a checkout. Automatic skill integration remains separate. Acceptance authorizes building this isolated toolkit; it grants no site repair, publication, monitoring or live collection. The implementation checks below have not run.

## Design

### Parallel ownership and invocation

All source, schemas, dependency lock, tests, fixtures, examples and the usage guide live in `tools/seo-evidence/`. A separate workflow, `.github/workflows/seo-evidence.yml`, verifies that directory. The ownership check permits those implementation paths plus this document's claim, task, status, evidence and review updates. No other existing implementation file or feature document is an edit target. If integration later requires changing an active feature's files, leave it for that feature's owner or a separate accepted integration task.

Expose three noninteractive commands through `bun tools/seo-evidence/cli.ts`: `snapshot --input <bundle.yaml> --output <new-directory>`, `inspect --snapshot <snapshot.json> --output <new-directory> [--policy <policy.yaml>]`, and `compare --baseline <snapshot.json> --current <snapshot.json> --output <new-directory> [--policy <policy.yaml>]`. Help and the example guide show complete commands. Configuration is strict YAML; generated snapshots and findings are versioned JSON. The local package keeps its runtime dependencies and strict TypeScript config within its own directory and uses a committed Bun lockfile. It does not require the vh-adlc binary, an agent login or any SEO subscription.

### Evidence bundle and coverage

Define bundle schema version 1 in the tool's schema and complete example files. Required top-level fields are `schema_version`, `captured_at`, `origins`, `entry_urls`, `pages` and `files`. `origins` lists exact allowed HTTP(S) origins; `entry_urls` identifies graph roots. `pages` is the declared observation inventory. An optional `sitemap_urls` inventory and optional `groups` map supplied URLs to named page-template groups. Group membership is explicit, not inferred from path depth or AI classification. Optional `extraction.main_selector` supplies the main-content CSS root selector; its default is `main`, and its effective value becomes part of the extraction identity.

Each page has its requested URL, outcome (`captured`, `failed` or `not_collected`), capture mode (`initial` or `rendered`), and observation timestamp. Captured pages must also provide a known final URL, HTTP status, response content type, selected response headers and a relative body-file path; a missing final URL is invalid input, never a fallback to the requested URL. Headers are limited to `Content-Type`, `X-Robots-Tag`, `Link` and `Location`, matched case-insensitively; a supplied Content-Type header must agree with the required content type. Header values are ordered lists so repeated directives are retained. Redirect chains are optional recorded ordered hops, never reconstructed from a canonical annotation; supplied chains must agree with the requested and final URLs. A page may supply only one observation per requested URL and mode in a bundle; duplicates are invalid. HTTP errors with captured responses remain captured status observations; a transport failure has unknown status. Files carry relative paths and SHA-256 digests. HTML bodies must be valid UTF-8 in v1; unsupported encodings fail visibly rather than producing replacement text.

Require every referenced file to be in `files` and to match its digest. Resolve only ordinary files within the bundle directory; reject absolute paths, traversal and symlinks. Reject unsupported versions, duplicate/unknown YAML keys, inconsistent URL/origin metadata, malformed required values and over-limit inputs before analysis. The v1 limits are 10,000 declared page observations, 5 MiB per body file and 250 MiB total referenced input bytes; exceeding a limit is a visible input error, never silent truncation. Do not resolve URLs through the network. URLs in content are data, never commands.

Provide a written mapping example for the existing Stackweaver saved export into this native bundle: use the retained HTML plus matching request status/headers/final URL and their hashes. Validate each mapped record instead of trusting the old summary. Do not silently accept arbitrary third-party JSON. Native schema support is required; general SiteOne/SEOnaut export importers are deferred.

Snapshot coverage records declared/captured/failed/not-collected counts and capture modes, all supplied roots and sitemap URLs, and per-group declared/captured/failed counts. Missing HTML or metadata caused by an input error is invalid. Declared failed/not-collected observations or unresolved final-document conflicts produce a partial snapshot with their reasons. A complete snapshot means its declared inventory was captured without those conflicts, not that the whole site was crawled. The snapshot retains extraction-version and settings identities, file hashes and relative evidence references. It never copies full response bodies or unrelated headers into findings.

### URL identity, parsing and graph

Use an HTML parser rather than regular expressions. Parse title, description, H1 text, document language, HTML/HTTP canonical annotations, page-control observations, JSON-LD presence/syntax, `a[href]` links, element IDs and legacy named anchors. Retain source multiplicity; combine controls as defined below rather than picking one source. Resolve links from the known final URL using the first `base` element with an `href` attribute, including an empty href; ignore subsequent base elements. Apply HTML's URL parsing/fallback rules: an invalid first base or a data/javascript base falls back to the document URL, while a mailto base remains non-hierarchical and cannot resolve a relative child. Filter resolved targets to HTTP(S) only after resolution. External browser-policy effects not represented by the saved evidence are unverified; this static graph does not attest browser execution. Extract all links, distinguishing links within the selected main-content root from links elsewhere.

Use standard URL resolution and serialize URL identity without fragments. Preserve path case, trailing slashes, percent-encoded path distinctions and the query string's ordering, repeated keys and values. Do not remove tracking parameters, sort queries, fold HTTP into HTTPS or merge hosts. Canonical and redirect relationships remain separate evidence; they do not silently equate URLs. Keep original hrefs and fragments for diagnostics. For captured successful HTML, follow HTML fragment selection: an empty fragment targets the document top; check raw IDs/named anchors before the percent-decoded UTF-8 form, with ID matching before named-anchor matching in each pass; if neither matches, apply the case-insensitive top fallback. Only an absent supported target is a broken fragment. Unsupported text/media fragments or undecidable decoding remain unverified, never broken solely because this extractor cannot evaluate them.

Analyze each capture mode separately. Document nodes use final URLs; requested URLs retain their own observation/redirect identities. Attach a captured document's anchors to its final node. Retain explicit recorded redirect hops as a separate edge type. When requested and final URLs differ but hops were not saved, retain a labelled observed final-transition edge whose intermediate hops/count are unknown; do not invent an HTTP chain or status. Roots may reach final documents through those recorded transitions. Anchor edges have weight one and redirect/final-transition edges weight zero for shortest observed anchor depth; report redirect evidence separately from link depth.

Several requests can reach one final URL. Retain all observation records. If status, media type, relevant headers, body hash and effective extraction settings agree, that final node uses the common facts and lists every source observation. If they conflict, report the final node as conflicting and partial; use none of those observations to select its status, outgoing anchors, fragments, duplicate content or regression values. Upstream links can reach that URL, but its content checks and onward paths remain unverified. Comparisons match observations by requested URL/mode and also expose final-URL changes; they do not silently rematch aliases across runs.

Retain edge source files and anchor positions, and compute incoming discovery links from other URL nodes; self-links do not establish discovery. Report pages with no observed incoming discovery and pages unreachable from supplied roots as candidates within this corpus; roots are exempt from zero-incoming findings. Use explicit zero-incoming findings only for supported, nonconflicting document nodes. A sitemap entry is discovery evidence, not an incoming content link. There is no default too-deep threshold or whole-site orphan verdict.

Classify link targets as captured-success, captured-HTTP-error, redirect-recorded, out-of-scope, conflicting or unobserved. An uncaptured target is not a broken link. Verify a redirected fragment only through saved, compatible final-document evidence; otherwise mark it unverified. A recorded redirect whose destination is unobserved never proves destination success. Keep all directed graph facts separate from ranking, PageRank, verified crawler or indexation claims.

### Duplicate groups and coverage by template

Find exact duplicate nonempty title and description values among captured successful HTML pages, partitioned by document language and capture mode; unknown language stays explicitly unknown. Normalize character whitespace only and preserve case. Keep canonical annotations and response state with every member so a human can distinguish intended variants from mistakes. Duplicate groups are candidates, not automatic consolidation/canonical instructions.

For main-content duplicates, use an explicit CSS root selector, default `main`, and remove script/style/template content before extracting text in DOM order. Require exactly one matching root; absent or multiple roots make that page's main-content comparison unavailable. Collapse character whitespace and hash the resulting nonempty text. Compare exact hashes only within the same selector, extractor version, language and capture mode. Shared navigation/footer text outside the root cannot create a duplicate-main-content finding. Do not label a short page thin or treat overlapping words as proven keyword cannibalization. Near-duplicate semantic detection and editorial recommendations are deferred.

For each optional page group, show its observed URL set, capture coverage and applicable findings. No sample is propagated to uncaptured group members. This adopts the useful coverage discipline of template sampling without introducing a browser sampler, lab score or arbitrary sample-size default.

### Technical comparisons and failure policy

Compare two explicit snapshot files. Reject different schema/extraction versions, extraction settings or origin scopes as incompatible. Match pages by requested URL and capture mode, preserve both timestamps and inventories, and report added, missing and unobserved pages separately. Status rules require captured HTTP responses in both observations, regardless of body media type. HTML-field regressions require successful captured HTML in both observations. Missing evidence stays unavailable and must not become a removed title, removed schema or a new HTTP failure.

Emit changes for status codes, titles/descriptions, canonical annotations, generic page index directives, H1s and JSON-LD presence/syntax. Generic index controls combine all `meta name="robots"` observations and unscoped `X-Robots-Tag` directives case-insensitively. Preserve crawler-scoped meta/header controls separately and exclude them from the generic result. Recognize parameterized directive names before interpreting a colon as a crawler qualifier; unknown/ambiguous syntax stays unavailable. Combine negative generic directives across sources, with `none` equivalent to `noindex,nofollow`; an `index` directive cannot cancel `noindex`. The noindex-added rule means the observed effective generic blocked flag changes from false to true. `none` to `noindex` alone is not a new block. This is a source-control observation, not a provider's actual indexing verdict.

Canonical observations include HTML head `link[rel~="canonical"]` resolved using the document base and valid HTTP Link-header canonical relations resolved against the final response URL. Parse HTTP Link syntax rather than comma-splitting URLs/quoted parameters. Retain each source; one unique valid target gives an observed effective canonical, no annotation means absent, and disagreeing or malformed annotations make it unavailable with a conflict/syntax finding. A source move from HTML to an equivalent HTTP header is not a canonical regression. Canonical-removed/changed predicates require a prior single valid target and a current unambiguous absent/different target; conflicts do not become guessed removals or target choices.

Other named regressions cover successful HTTP response becoming captured 4xx/5xx and a nonempty title or H1 disappearing. A changed or removed JSON-LD block requires review, not a lost-rich-result claim. Preserve raw evidence and normalized old/new values. Provider-specific robots.txt policy, Google-selected canonicals and AI-training policy remain outside the tool's claims.

The policy YAML has schema version 1 and `fail_rules`, a set of documented rule IDs. The empty set is the default. Unknown IDs are invalid; there are no severity/score thresholds or wildcard rules in v1. `inspect` can enforce its documented static rules for captured broken links, broken fragments, duplicate titles/descriptions/main content and observed-graph unreachable candidates. `compare` can enforce its documented regression rules. Selecting a rule that does not apply to the command is invalid. Do not modify any repository policy or CI pipeline while analyzing evidence.

Exit 0 means analysis completed and no selected rule failed, even if report-only findings exist. Exit 2 means invalid/incompatible input or partial declared capture; it never means clean. Exit 3 means complete analysis with a selected rule violation. When a partial analysis also contains selected-rule violations, exit 2 takes precedence and the report preserves both facts. Each output has explicit `analysis_status` and `policy_status`; do not conflate report-only findings with passing SEO or absence of defects. This feature adds no automatic deployment block to a consumer repository.

### Output, retry and verification delivery

Produce `snapshot.json` and `manifest.json` for snapshot, and `findings.json`, `findings.csv`, `report.md` and `manifest.json` for inspect/compare. JSON has schema version 1, tool/extraction version, input digests, capture/scope metadata, findings, coverage and statuses. The normalized snapshot contains the extracted facts and content hashes needed by inspect/compare; they do not reopen the original HTML. A finding identifies its rule, affected URL/mode, evidence paths/hashes and observed values. Stable IDs derive from rule, URL/mode and affected evidence identity; outputs sort by rule and URL. Reprocessing the same input/policy yields byte-identical analytical files in a new output directory. Include no current wall-clock timestamp or absolute local path in those files. CSV/Markdown escape source text so page content cannot become formulas, code execution or a forged report heading. Tool data is not an agent instruction.

Output directories must be new and exclusively created. Create an `INCOMPLETE` marker first, write files via temporary names, then publish `complete.json` with the manifest hash only after all file hashes verify and remove `INCOMPLETE`. Consumers require the verified manifest/completion marker and absence of `INCOMPLETE`; an interrupted finalization is safely refused. A fully written partial-capture snapshot may carry the completion marker, but retains partial analysis status and exit 2: artifact completion does not mean complete site coverage. A write failure or cancellation leaves the labelled incomplete directory, which is never accepted or overwritten on retry. Concurrent runs with distinct outputs are independent; two runs selecting the same output have one creator and one refusal. Inputs and other sessions' outputs remain read-only. A retry uses a fresh directory; there is no hidden baseline database, implicit latest selection, scheduler or delivery permission to replay.

Human status output follows the pinned terminal-output standard: explicit outcome words with its status symbols on TTY, an ASCII/plain option, append-only plain output without ANSI on non-TTY, and `NO_COLOR` handling. `--json` writes one undecorated result object to stdout; diagnostics go to stderr. That object retains the same status/exit semantics as file output. No interactive prompt, spinner or browser is needed.

The deliverable is the self-contained source directory and documented Bun command, not a new Go binary or installed plugin release. Verification runs the tool's frozen dependency install, strict type check, all tool tests and the complete example commands. A new path-filtered workflow runs those same checks for changes to the directory or itself, using the repository's existing action-pinning and Bun policies. It performs no live crawl and uploads no site evidence. Existing workflows and plugin version/manifests remain unchanged. A later plugin integration must recheck its own package/version and authority requirements.

No existing output requires migration. Unsupported future input versions fail visibly; old bundles/snapshots remain available to their original tool version. Rolling back the source leaves saved evidence intact and introduces no site-state rollback. Compare snapshots only when their extraction identities match rather than rewriting old evidence to fit a new version.

### R-1

FINDING: F-01
KIND: factual
SEVERITY: blocking
WHERE: Context / Owner summary, line 23; Design / URL identity, parsing and graph, lines 76-82; Design / Technical comparisons and failure policy, line 98; AC-03; Test Plan / AC-03
EVIDENCE: Line 78 specifies decoded-fragment lookup against captured target IDs. That is insufficient to determine whether an HTML fragment is broken. The HTML Standard's fragment-resolution algorithm also recognizes an empty fragment, the top-of-document fallback, named anchors, and an undecoded identifier before its decoded form. See https://html.spec.whatwg.org/multipage/browsing-the-web.html#scroll-to-fragid. The cited saved Stackweaver homepage contains href="#" and no empty ID. Applying the specified lookup would therefore allow a working link in the actual input corpus to become a broken-fragment finding and an opt-in policy failure. The test row covers good/missing IDs but none of these valid alternatives.
PROPOSAL: Specify HTML fragment resolution, including raw and decoded matching, named anchors and top-of-document cases. Add fixtures that must remain valid alongside genuinely missing targets; classify unsupported fragment forms as unverified rather than broken.

FINDING: F-02
KIND: factual
SEVERITY: blocking
WHERE: Design / URL identity, parsing and graph, lines 76-80; AC-03; Test Plan / AC-03
EVIDENCE: Line 76 selects the first valid HTTP(S) base URL. HTML instead uses the first base element with an href attribute and ignores subsequent base elements, including when the first value causes fallback. See https://html.spec.whatwg.org/multipage/semantics.html#the-base-element. For a document containing <base href="mailto:somebody@example.com"><base href="https://example.test/later/"><a href="child">, the specified selection invents an HTTP edge to https://example.test/later/child. The actual first base does not permit resolving that relative URL. An observed Bun URL check returned an unresolved target for the mailto base and the invented HTTP target for the later base. The test plan exercises only a valid base.
PROPOSAL: Follow the first-base-element and fallback rules before filtering resolved link targets to HTTP(S). Add multiple-base, invalid-first-base and non-HTTP-first-base fixtures that assert the actual resolved target or unavailable resolution.
