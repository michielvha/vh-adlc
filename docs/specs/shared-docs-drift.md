# Shared documentation drift

Find accumulated documentation problems across a repository, then turn verified proposals into one reviewable change. The shared operation has audit and resolve modes.

For example, an old guide links to a moved source file. The local scanner flags the link; the shared workflow reads the guide and current source before proposing the correction. A stale audit PR gets checked again before its change is reused.

| Shared in vh-adlc | Retained in the adopting repository |
| --- | --- |
| Audit and resolution procedure, finding dispositions and concise reports | Scanner implementation, roots, detector exceptions and thresholds |
| Recheck proposed edits against current source and preserve human decisions | Documentation styles, generated indexes, site and visual checks |
| Distinguish a wrong detector from a wrong interpretation | Suppressions, corrections history, schedules and publication permissions |

The scope excludes claim-by-claim docs-truth sweeps and their rolling ledger. Existing docs impact continues to handle the documentation affected by one selected code change.

## Scope

Include one harness-agnostic docs-drift operation with audit and resolve modes, a consumer configuration/scan-result contract, reports, bounded verification helpers, examples and Stackweaver migration tests.

Audit consumes a local scan and feedback history, verifies candidates against current source and prepares a concise report. An explicitly authorized prepare run may also produce bounded safe edits for a consumer-owned advisory workflow. Resolve rechecks selected old proposals, deduplicates them and prepares their verified subset plus a ranked decision list.

Keep the scanner and detector semantics local. Preserve Stackweaver's current command, advisory scheduling, source/index/visual rules, historical exemptions and feedback files through thin forwarding instructions. Do not change schedules, provider/model selection, secrets or notification behavior as part of extraction.

Excluded: docs-truth/sharding, a new universal scanner, detector-rule changes, product code repair, unrestricted autonomous publication, a replacement for feature acceptance/review gates, and migration of unrelated agents or active drift PRs. Live backlog resolution requires a separate selected run after adoption.

### Entry and consumer contract

Add `vh-adlc-docs-drift` as a content operation with explicit audit and resolve intent. Read local instructions and resolve the existing pinned conventions. Keep the canonical procedure independent of model, shell-session persistence and harness-specific tool names. Missing prerequisites produce a setup handoff, never reconstruction of the retired agent.

Use `.vh-adlc/docs-drift.yaml` and the verified binary's strict YAML reader exported by `scripts/settings-file.ts`. For committed assessment or current-default policy, obtain the exact Git blob bytes and pass them to `readYAML`/`createYAMLReader`; hash those same bytes. Do not call the working-tree `settingsFile` reader to stand in for a remote/default blob. In an owned clean checkout whose bytes match its bound commit, `settingsFile` may enforce local naming/suffix conventions. No dirty or candidate policy substitutes for the default-branch gate. A docs-drift validator owns its schema/version and meanings; no second YAML parser or alternative file suffix is added. PR discovery reuses the GET-only paginated `scripts/github-read.ts` reader and preserves its completeness/error observations. Incomplete selected PR collection is an assessment gap and cannot authorize resolution or superseded-PR closure.

Reuse `hash` and the Git-read helpers exported by `scripts/audit/snapshot.ts`; these perform no repository writes but are not pure functions. Use byte-exact `gitBytes` with NUL-delimited Git output for paths/inventories and raw bytes for blobs. Never use the trimming `git` wrapper for a filename or content; restrict it to validated scalar IDs. The existing module imports audit settings/inventory and can return audit-labelled Git errors; preserve the actual failure as an assessment gap rather than hiding it or inventing a new parser. Protocol digests use the byte-ordered canonicalizer defined below, not audit's locale-dependent `digest` ordering. Add that small protocol utility within `scripts/docs-drift/`; it contains no YAML parser or detector logic. Do not call its audit-specific `captureSnapshot`, which requires a persistent finding ledger and code-audit modes. The new `scripts/docs-drift/settings.ts`, `snapshot.ts`, `scan.ts`, `report.ts`, `adoption.ts` and `cli.ts` provide docs-drift validation, input binding, scan checks, report formatting and installed adoption consistency. They do not implement structural detectors. Do not import maintenance or audit `adoptionPreflight` directly: those helpers hard-code their own operation name, helper stages and CLI paths, while audit also binds its ledger policy and mode effects. The new adoption helper has separate operator-verification and runtime-gate modes. Operator verification follows their artifact-hash/payload/consumer/native-install consistency pattern with docs-drift evidence. Runtime checks use the portable committed attestation contract below, without a private operator artifact root. Both retain the operator-attestation limitation; neither grants permission or enforced truth proof.

Add a lifecycle route for whole-corpus documentation drift and stale documentation-audit proposals. “Scan all docs for accumulated drift” selects audit; “recheck and consolidate these docs-audit PRs” selects resolve. “Finish closing the audit proposals consolidated in merged PR #N” selects resolve's explicit post-merge sub-mode, not another advisory scan or an automatic replay of edits. “Which docs does this patch affect?” stays docs impact, a plain doc edit stays artifact editing, and persistent code-audit intent stays `vh-adlc-audit`. A request to verify claims exhaustively stays the selected local truth workflow or gets an unsupported-operation handoff. Ambiguous “audit” or “audit the docs” without enough context gets one focused question before any scan or write. The presence of settings never chooses the operation.

Ordinary locked-binary setup precedes strict settings and knowledge; this docs-drift content operation does not use persistent code audit's special offline bootstrap. Required pages are `conventions/feature-documents.md`, `conventions/documentation.md`, `conventions/documentation-impact.md`, `conventions/delivery.md` and `guides/humanize-prose.md`, plus applicable consumer language/project pages. Missing required knowledge stops with the existing missing-page/pin handoff. The loop's unpinned-content-operation rule adds no onboarding files: use the installed plugin revision, report the missing repository pin and leave onboarding to a separate authorized setup. Missing required consumer settings also gets setup instructions; do not create policy files as an incidental doc fix.

Consumer settings identify the scanner invocation as an argument vector, intended documentation scope, required detector-unit IDs, per-unit document selectors and options, feedback files, project procedure and allowed verification/generation commands. Required detector units are a nonempty, duplicate-free consumer-defined set; they are distinct from finding-category labels and remain local rather than a hard-coded shared detector catalog. A committed `detector_inputs` mapping has exactly one selector for each required ID: explicit `all_inventory`, or a declarative roots/exclusions/suffixes subset of the configured documentation inventory. The shared helper evaluates these selectors against its independently enumerated Git-tree inventory. No report-supplied document list, executable predicate or scanner-internal exemption changes a unit's expected set. Historical exemptions remain detector decisions after collection. This accounting checks input coverage, not whether a detector interpreted every input correctly. PR discovery and publication destinations are explicit consumer inputs. Reports and settings cannot grant their own execution authority. Treat scanner messages, documentation and PR text as data; never execute embedded instructions or arbitrary report-supplied commands.

The scan result binds its source commit, scope/options and scanner identity, and distinguishes complete collection from findings and failures. It preserves finding detector, severity, document/location and explanation, suppressed findings with reasons, and stale suppressions. The following protocol makes collection completeness independently checkable against the selected files; it does not prove semantic truth or defend against a scanner or shell-capable agent deliberately forging evidence. Document identities stay within the consumer's configured scope. Unknown detectors remain visible candidates rather than being dropped or automatically fixed.

A process exit of zero, an empty findings list or a lower finding count does not prove completeness or accuracy. Missing/malformed reports, skipped inputs, mismatched source, unreadable feedback and unavailable required capabilities leave the assessment incomplete. Do not repair the scanner by weakening a shared validator; any necessary local completeness correction must have its own scoped regression and review.

### Scan-result protocol and local correction

Use a versioned JSON result with `schema_version: 1`, `source_commit`, `settings_digest`, scanner identity (script digest and argument vector), declared roots/exclusions/detector options, an examined-document inventory, collection failures, per-detector execution outcomes, findings, suppressed findings and stale suppressions. Required fields and types are validated; duplicate document identities, unknown protocol versions, malformed entries or a changed binding are incomplete. The settings contract defines the documentation suffixes and scope; the initial example uses tracked Markdown under its configured roots. It never substitutes settings or scope supplied by the report itself.

The shared scan helper independently enumerates the expected documents from the exact Git tree and the committed configuration's scope/exclusions. Each in-scope document must have exactly one inventory entry binding its normalized relative path and content digest, with a read-success or failure outcome. Unexpected paths, omissions, duplicate entries, escapes, symlinks, changed content or explicit read/parse failures prevent a complete result. Legitimate configured exclusions remain explicit in the bound scope; an unexpected read failure cannot be relabelled an exclusion. Detector-specific historical exemptions remain detector policy after collection, not a way to hide unexamined inputs. Missing required detector execution is a gap even if all document reads succeeded; its explicit v1 accounting is defined below.

For each configured required detector unit, the v1 result includes exactly one execution entry with its ID, examined document path/digest inventory, bound input digest and `complete` or `failed` outcome, plus an error on failure. The helper independently derives the applicable set from committed `detector_inputs` and requires exact equality with the unit's examined inventory; a complete unit over a strict subset is incomplete even if every document was read globally. A successful unit with no applicable files is complete with an explicit zero-input count; it is not silently omitted. Missing, duplicate, skipped, failed or differently bound required units make the assessment incomplete. Additional unknown finding categories remain visible as candidates; they do not replace missing required execution. The bounded Stackweaver correction emits this execution accounting as well as document accounting, without changing detector rules. Tests include all documents read but a required detector absent or throwing, and require incomplete despite a lower finding count.

Protocol v1 uses lowercase SHA-256 hex of raw content bytes, not a Git blob OID or decoded/normalized prose. Successful document entries must match the bytes of their blob at `source_commit`; failed reads record a failure and a null digest when no bytes were obtained. Paths use repository-relative Git-tree identities with `/` separators, preserving case, Unicode and literal filename characters; reject invalid UTF-8, absolute paths and `.`/`..` traversal rather than replacing or aliasing names. Never reinterpret a literal backslash as a separator. Sort applicable document entries by their UTF-8 path bytes. A detector input digest is SHA-256 of canonical UTF-8 JSON with exactly these keys: `source_commit`, `settings_sha256`, `scope_sha256`, `feedback_sha256`, `detector_id`, `options` and `documents`. Settings and each feedback-file digest are SHA-256 of raw Git blob bytes, never a parsed YAML value. `scope_sha256` hashes the canonical object with exactly `roots`, `exclusions`, `suffixes`, `required_detectors` and `detector_inputs` (sets and per-selector path/suffix sets sorted by UTF-8 bytes); `feedback_sha256` hashes the sorted `[path, raw_blob_sha256]` array; `documents` is the sorted applicable `[path, content_sha256]` array independently derived from the committed unit selector, and must equal that unit's examined inventory. Canonical JSON has no insignificant whitespace, sorts every object key recursively by UTF-8 bytes without locale comparison, preserves array order except the specified set/path sorts, and uses JSON string/finite-number serialization. Reject invalid encodings, unpaired surrogates and unsupported/non-finite values. The scanner/adapter must read/hash Git blob bytes, or refuse a checkout whose filters/EOL conversion changed them. Cross-implementation golden fixtures cover mixed-case and non-ASCII option keys and filtered checkouts. Required Git-history or other bound inputs must be available; an unavailable input makes that detector failed/incomplete, not a zero-findings success.

An initial assessment uses a clean committed source. After authorized edits, the verification scan binds a new authorized local checkpoint commit; it includes any added/deleted documentation and regenerated outputs. Before that checkpoint, reports may describe a provisional diff, but cannot establish publication readiness. This avoids claiming committed-source verification over unrelated dirty or unrecorded document overlays.

Include the minimal Stackweaver correction in this migration: `scripts/docs-audit.js` records read/parse outcomes and document inventory instead of silently continuing on read failure, and emits the bound protocol directly or through its local adapter. Its existing advisory/strict exit semantics and detector findings remain unchanged; consumers inspect protocol completeness separately. Add meaningful local regressions in `scripts/docs-audit.test.js` and migration contract tests in `tests/agent-docs-drift/`: inject an unreadable/skipped document, observe the old omission, then require an explicit failure/inventory mismatch and an incomplete shared result. Compare ordinary findings and suppression behavior before/after to detect unintended rule changes. Independently review this bounded correction before consumer cutover; migration approval does not authorize applying its real findings.

### Audit and preparation

Use one exact owned assessment tree for the scan, source inspection and proposed changes. Recheck the source and selected inputs before acting; preserve unrelated dirty work. Read relevant prior corrections and suppressions before adjudicating a finding.

For every candidate, inspect the document and supporting code and record confirmed drift, still accurate or unknown, with evidence and a recommendation. Recency, an existing audit diff and a detector category do not establish truth. Keep intended contracts, historical records, deliberately incomplete matrices and other-system references intact. A product bug is a separate finding, not permission to rewrite the documented intended contract.

Standard feature-document protection is explicit: prepare/resolve never edits Scope, Design, Acceptance Criteria, Test Plan or normative `covers` in a standard feature document. It never edits any part of a `branch`-claimed feature document on its own drift branch. Report the proposed correction and route normative revisions to `vh-adlc-spec` or the existing claiming writer with the required handoff; do not change status to bypass that route. Reuse committed feature-format/root classification and strict metadata reading rather than guessing from filenames. Local-format consumers keep their actual plan rules and ownership gates, and mere source presence still cannot satisfy runtime acceptance checks. Tests include a planned standard spec with stale Design, stale normative coverage and a claimed in-progress document, all byte-preserved with the correct handoff.

Also inventory ordinary document paths covered by other features. Report every affected feature and the resulting implementation-review staleness; changing an ordinary covered doc does not silently preserve a fresh implementation review or reopen a terminal feature. If a path belongs to an in-progress/other active claimed feature or another current writer, do not edit it on the drift branch without the claiming writer's handoff or the owner's explicit coordinated selection of that overlap. Otherwise retain it as a proposal to that writer. Closed historical feature coverage is reported as historical staleness, not treated as a permanent reservation of every covered document; selected new work still preserves the old feature's scope/status and follows its own review. Test a guide covered by an in-progress claimed feature, an explicitly coordinated case and a document covered only by a closed feature, alongside the protected feature-document cases above.

Report mode leaves consumer docs, feedback, indexes, Git index and refs unchanged, saving a report only at an explicitly selected output location. An authorized prepare run edits only confirmed, bounded corrections within its owned scope. Moves, deletions, merges, pruning, ambiguous fixes and substantive plan/status decisions require explicit selection. Feature documents retain their own review/gate rules; source presence alone does not establish runtime criteria or authorize ticking them.

The owner-facing report starts with a short explanation, proposed/applied fixes and decisions with recommendations. Keep the full per-finding evidence and unknowns available below that summary. Never claim all findings were verified when only a subset was inspected. Where a harness cannot delegate independent nontrivial checks, record the missing verification and retain the affected recommendation as provisional.

### Resolution and feedback

Resolve discovers only the selected consumer/PR scope, reads complete proposal bodies and diffs, and takes a fresh scan from the current owned base. It classifies every selected hunk as apply, apply-modified, already fixed, wrong or defer. Deduplicate identical proposals; conflicting suggestions require current evidence, not a newest-wins rule. Preserve uncertain proposals in the decision report.

Complete proposal input means more than the paginated PR list. Obtain repository/PR identity, full body, exact head SHA and observed base SHA through the GET reader. In a recorded owned assessment object store, read-only-fetch the selected target repository's exact PR head and base objects, verify the head matches the observed metadata, derive their merge base and compute the full local Git diff including the complete file inventory, additions/deletions, renames and any binary blob identities. Do not use optional/truncated REST `patch` fields as authoritative hunks. Fetch objects only into that owned store (without changing caller refs/index or checking out its files), from the verified consumer origin and its fixed PR ref; never follow a report/body-supplied clone URL. Bind the proposal to repository, PR ID, body digest, head/base/merge-base SHAs and diff digest, and recheck them before effects.

Missing objects/history, a changed head, unreadable or truncated diff, omitted file/hunk or exceeded processing bound makes that proposal incomplete. It contributes no applied hunks and cannot be closed. Other proposals can still be inspected, but the selected run cannot claim complete readiness by silently dropping an incomplete member; get complete inputs or an explicit scope reselection. Binary changes require a concrete disposition and the consumer's actual asset checks rather than pretending a missing textual patch is no change. Test large diffs, omitted REST patches, unavailable objects, changed PR heads and incomplete file inventories with caller refs/index preserved.

Rebuild the verified subset on a fresh owned branch instead of replaying entire stale audit commits. Report which source proposals contribute which exact changes. Approval for one decision does not approve the rest. Revalidate source, proposals and approved decisions after material changes.

A selected proposal is superseded only when every hunk has a reviewed disposition: applied/apply-modified in the merged consolidated PR, already fixed with current evidence, wrong with the appropriate feedback delivered, or explicitly carried as a deferral/owner decision in that merged PR's decision list. Uncarried deferred or undecided hunks keep the original proposal open. Superseded closure requires separate actual closure authority and happens only after the consolidated PR is observed merged from its reviewed head, with its selected hunks, feedback and carry-forward verified against the delivered result. Merely opening/publishing the replacement is insufficient. Post an authorized explanation linking that merged PR and the per-hunk dispositions before closing. An abandoned or closed-unmerged replacement leaves every original proposal open. Publication/merge failure, missing feedback or incomplete carry-forward denies closure; this workflow never grants merge authority by proposing supersession. For closure, first load and freshly review the durable resolve record through the post-merge entry described below. GET-observe `merged: true`, the consolidation's unchanged head SHA equal to the independently reviewed published checkpoint, its merge-result commit, and the selected original proposal heads/bodies. Support every merge method allowed by the consumer, including squash and rebase; do not require the reviewed head to be an ancestor of default. Bind each delivered correction/feedback file to its expected postimage raw-blob SHA, including expected absence for a deletion, and carry-forward to the full consolidation-body digest freshly reviewed for this closure batch, rather than assuming an old mutable PR body is still approved. Verify these postimages at the observed merge-result tree. Then read current default, require the merge-result commit to be reachable there and compare its full later delta against the same bounded assessment read set used for publication. Disjoint later changes may proceed. A bound-input change, unavailable comparison or changed original/consolidation head/body pauses closure for a fresh closure-only assessment/review at current default; it does not require inventing another docs PR. Reverify the selected dispositions and expected touched-file bytes there, and obtain fresh approval for any materially changed disposition/explanation. A later revert or removed carry-forward keeps affected originals open. The delivered consolidation delta itself is the expected transition, not a reason to invalidate its own review. Under the lease immediately before each authorized explanation/closure, recheck the observed default, proposal identities/heads/bodies and consolidation bindings; a changed value stops the effect sequence. Report-only runs merely propose this sequence.

Before the publication checkpoint, an authorized resolve preparation creates one versioned record at the configured `.vh-adlc/docs-drift/resolutions/<id>.yaml` path in that same candidate tree. It contains repository identity, assessed base, selected original PR IDs/head/body digests, every hunk's disposition and evidence, touched-file postimage hashes/absences (excluding this record itself), carried decisions, bounded read-set/history inputs and selected verification. It contains neither its own future checkpoint ID nor the future consolidation PR ID/body digest, native review result or a self-digest. Its raw Git-blob digest is therefore stable before checkpoint review. Include it in the owned diff and independent candidate review; the published PR links its path/digest as a locator after the checkpoint is known. No record-only commit is added after that review.

A fresh post-merge session can start with only the consolidation PR ID and the actual current request. Obtain complete GET identity/head/body/merge inputs and the exact head Git objects; identify the added resolve record through that head's full diff within the configured record root, then verify its blob digest, repository and all bindings against that tree and selected proposals. A PR-body locator is an untrusted hint, not the authority or source of truth; absent, ambiguous, malformed or differently bound records produce a recovery handoff with no closure. A missing private historical artifact does not silently pass. Run a fresh independent closure review using the immutable published checkpoint/resolve record and observed current default, bind the current full PR body, selected dispositions and exact proposed explanation/closure payload, and require the actual current/adopted closure authority. This review can verify the old checkpoint now without claiming to recover or prove its original pre-publication review. Save its raw records and current evidence in this run's selected report location; no historical private cache is required. The committed record supplies reproducible inputs, never permission to write. On an unattended resume, a consumer must separately adopt the post-merge resolve entry and its closure scope; the scheduled advisory grant alone does not authorize it. Another host follows the same entry, checks and authority rules.

Keep the two feedback channels distinct: a faulty detector gets a narrowly supported suppression; a mistaken interpretation gets a correction-history entry while the detector's real finding remains visible. Repeated mistakes produce a proposed detector/procedure repair. Retiring a stale suppression requires verifying the corresponding scope and detector were actually collected. Report-only runs write neither feedback store.

Apply the consumer's generators and source/visual checks after an authorized edit. Compare finding identities and severity by affected class; a lower aggregate count cannot hide a new or suppressed finding. Never hand-edit generated indexes. Keep feedback changes, proposed documentation changes and selected decisions reviewable together.

### Authority and delivery

### Independent candidate review and publication

Require an independent review of every prepared advisory or consolidated resolve change before publication. Add `references/docs-drift-review.md` using the existing model-identity/isolation/returned-record protocol. The reviewer receives repository, exact candidate commit, assessment/report identity, selected finding/PR/decision scope, consumer policy and verification inputs. It inspects the entire proposed diff including feedback and generated files, checks source-grounded dispositions and authority, and runs or inspects the required checks. Per-claim verification is additional evidence, not a substitute for this candidate review.

A local checkpoint commit precedes review only when the run actually authorizes that commit; a permission to edit does not imply permission to commit. The scheduled prepare worker emits its bounded edit manifest and body without staging. Its authorized local wrapper stages only that owned manifest, makes the checkpoint, runs the read-only independent reviewer and publishes only after a clean matching result. No broad `git add -A` or partial/failed model return becomes success. Record native model identity, exact target and unmodified returned findings with their provenance outside the checkpoint tree, then include the evidence in the published artifact/PR through the authorized wrapper. Both production and trial publish the exact independently reviewed candidate commit and tree. No record-only commit is added afterward. Review records and native evidence remain in the PR body and separately retained external artifacts; any source-tree evidence file must already be present in the reviewed checkpoint. A changed head requires fresh candidate review, even if its only change is described as evidence.

Changed source/diff, settings, scanner/options/scope, feedback, selected PR heads/bodies or owner decision payloads invalidate the review and require revalidation/review. A missing reviewer, model mismatch or blocking/should-fix finding prevents publication. Interactive candidate review follows the existing protocol: a current owner-requested model must match; without one, the configured host default and its honestly reported identity follow that protocol. Unattended publication additionally requires a committed nonempty `candidate_reviewer.requested_model` in consumer policy, with the provider selecting that model without fallback. Bind the same expected identity in the trial definition and adoption record. Compare the native returned `MODEL:` using the protocol's family/full-ID rule; a different or `unknown` identity denies unattended publication. This field records the owner-selected local reviewer; extraction does not change provider/model selection or invent a shared default. Missing model policy is a setup handoff before the trial, not an instruction to spend or alter credentials. Reports remain available with their limits. This is an operator-reviewed workflow, not a new enforced-proof controller or an implicit permission to make remote changes.

Base freshness has a mechanical rule. Bind the assessment to its exact base commit and input read set: the configured document, source and reference roots (including negative/absence searches), settings, scanner/adapter, feedback, worker/procedure, generator and verification inputs, plus required Git-history inputs. Default to the whole tracked repository when that read set cannot be bounded completely. Under the lease, read the current consumer default and compare its full delta from the assessed base against that binding. A non-descendant base, unavailable comparison or any bound input change requires a fresh scan, verification and independent review. A current default advance disjoint from every bound input may be recorded as unrelated and does not invalidate the original reviewed checkpoint; do not rebase, regenerate or amend that checkpoint to follow it. Record both observed revisions and the disjoint delta in publication evidence. If a required history/time input changes, it is material even when paths are otherwise disjoint. Tests show an unrelated out-of-scope advance may proceed with the same reviewed head, while an in-scope/settings/feedback/verification/history advance cannot.

The single authoritative real-corpus publication gate is the `publication` block of committed `.vh-adlc/docs-drift.yaml` at the freshly observed consumer default branch. It names `mode: staged|adopted`, the exact publication lease ref and committed adoption-record path. Read that record as a Git blob from the same default commit and compute its digest at observation time; do not put the record's own digest into the settings it binds. Missing or staged configuration denies shared real-corpus push, PR and closure effects even when a generic current request asks to publish. A publication request is not a cutover-state transition; changing the staged policy requires the explicit reviewed adoption procedure or a separate owner-authorized policy revision. Candidate-branch or dirty configuration, reports and cached receipts cannot replace current default policy.

`adopted` is necessary, not sufficient: the runtime gate checks the referenced committed adoption attestation's schema, recorded passing-trial and paired-review verdicts/identities/digests, exact current component/worker/reviewer/publisher bindings and expected route. Operator-time verification of the original artifact bytes is a separate prerequisite before authorized adoption delivery, as defined below. It does not require a post-cutover observation to permit the first adopted publication; the non-circular assembly and later completion evidence are defined below. The mode does not grant any effect; the actual request/adopted consumer grant is still required. Recheck policy and review bindings under the lease immediately before remote effects. Rollback treats this block and record reference as migration-owned: first quiesce shared publication under the same lease, then restore staged mode together with the legacy worker route through normal authorized consumer delivery. A previously adopted local candidate or cached receipt must then be denied by current-default policy. Tests cover missing/pre-cutover mode, a generic publish request before cutover, stale adopted candidate configuration after rollback, and denied shared effects when the legacy worker is restored.

Routing is explicit at every stage. Before cutover, the existing `.claude/commands/docs-drift.md` and its harness-neutral Stackweaver resolver entry continue to select the legacy resolver for its existing selected publishing/closure flow; the scheduled entry selects the legacy auditor. The new direct shared operation is available only for report/local preparation and has no real-corpus publishing route in this state. At cutover, the same reviewed consumer change that commits `publication.mode: adopted` switches both the interactive command and scheduled worker to shared forwarding instructions and disables/replaces every legacy real-corpus publication and closure entry. Frozen legacy instructions are rollback artifacts, not additional active agents. A current entry must refresh its committed policy/routing before effects; an obsolete cached instruction is not a supported alternative publisher. Post-cutover tests attempt the old interactive entry against the shared scheduled publisher and require shared forwarding/lease coordination or a refusal, never a concurrent legacy write. Rollback atomically restores staged policy and both legacy entries under the publication transition procedure.

During the staged interval the unchanged legacy publisher does not participate in the new lease. Therefore shared interactive adoption is report/local-prepare only: shared real-corpus push, advisory/resolve PR publication and superseded-proposal closure are unavailable until the scheduled cutover. Keep the legacy publishing routes explicitly available under their existing consumer procedure; do not silently reconstruct or substitute a retired worker when setup fails. This is a declared migration state, not a ready publication mode. Test an active or newly starting legacy run against a shared resolve request and require denial of every shared real-corpus publication/closure effect. The only pre-cutover shared remote trial is the separately authorized synthetic, disjoint trial described below; it cannot touch real proposals or their namespaces.

After scheduled cutover, serialize the shared scheduled worker and a local resolve publisher for the same consumer through one cooperative repository publication lease. Only a run already authorized for the selected publication may create its named ephemeral lease ref; the adoption procedure names that acquire/release effect and its exact ref namespace. Atomically create the lease, record its exact object/run identity, and stop if another run owns it. Under the lease, recheck the current base, PR selections and reviewed candidate before pushing or closing superseded proposals. Release by an atomic comparison with the exact recorded lease object/run, only while still owned by that run; never force-take a foreign lease or infer ownership from its age. Interrupted or ambiguous ownership leaves a visible pending state for explicit reconciliation. This adds no merge, broad branch deletion, protection bypass or release authority. Authority and race/recovery tests cover the lease as well as the actual publication effects.

### Scheduled worker and staged adoption

Keep Stackweaver's schedule, selected provider/model and credentials local. Its future shared worker obtains the published vh-adlc source at an exact full commit corresponding to a verified release, loads the plugin directory through the provider's supported mechanism and verifies its component digest/version against the adopted installed payload. Put exact source repository/commit/release, plugin version and component SHA-256 in a separately committed immutable YAML pin under `.vh-adlc/docs-drift-components/<id>.yaml`, read through the existing strict reader. The reusable worker accepts an explicit `component_pin` path and validates its bytes against the selected adoption/trial manifest; there is no floating latest or report-supplied path. The active caller selects the approved pin, and a trial caller selects only its current-default trial-defined candidate pin. Track both source release and plugin version explicitly; they need not have the same version number. Keep the source SHA and release annotation visible to the project's existing dependency updater, with an extraction fixture for that pin. Updater proposals do not authorize automatic route changes or waive adoption/review checks.

Consumer adoption proceeds in three visible stages. First publish and marketplace-verify the shared component, then adopt interactive report/local preparation while retaining all legacy real-corpus publishing routes. First adoption requires both the actual unattended advisory trial and the installed-model synthetic resolve/closure collector trial defined below; neither substitutes for the other. Next, under separate publication authority, add a dispatch-only trial workflow such as `.github/workflows/docs-drift-shared-trial.yml` to the consumer's default branch; it has no cron trigger and does not replace the existing job. Finally, only after the observed trial, paired review and normal checks, switch both interactive and scheduled routes, retire/disable all legacy publication/closure entries and enable shared real-corpus publication in the same reviewed change. This is one shared implementation feature, with staged consumer adoption.

The real unattended trial means an actual hosted runner and selected provider/model, loading the exact published component and executing its assessment/preparation, independent candidate review and GitHub advisory handoff. Its inputs are a committed bounded synthetic documentation/code/feedback fixture in an isolated scratch Git repository, using the consumer scanner and trial-scoped settings. It does not inspect or resolve the live documentation backlog. The actual handoff is a draft PR in the selected consumer repository, on a unique `docs-drift-trial/<run-id>` branch, containing only identified synthetic fixture output under `tests/agent-docs-drift/fixtures/trial-output/`. Its body identifies synthetic findings and exact bindings. This exercises actual provider loading, runner permissions, candidate review and remote publication without publishing real findings or superseding any real PR. The trial publication lease and namespace are disjoint from legacy real-corpus proposals, and tests prove its allowed file/PR/branch scope cannot expand into them. Trial setup, paid/provider execution, draft-PR creation and exact owned cleanup all need a separate explicit authorization; accepting the spec grants none of them.

The unchanged publisher uses a manifest with separate `publication_repository`/`publication_base_commit` and `source_bindings`. Production normally has one consumer source binding. The trial's publication base is the freshly observed consumer default commit used for its owned branch, never the unrelated scratch commit. Its source bindings record the immutable fixture repository/commit/digests plus the consumer's scanner, worker, procedure, settings and verification read set. Ancestor/default-advance checks compare the consumer default with that consumer publication base; each additional source binding is rechecked against its own repository and immutable objects/digests. The scratch commit is not required to be an ancestor of consumer history. This is the same manifest-driven freshness algorithm in trial and production, not a trial-only bypass.

A committed `trial` block in current-default `.vh-adlc/docs-drift.yaml` names the trial-definition path and raw-blob digest. That committed definition binds the actual consumer/destination, permitted fixture bundle/source bindings, exact output-path and branch namespace, disjoint trial lease ref, worker entry and allowed draft-only effects. The separate trial authorization explicitly covers acquiring and exact-owned releasing that lease. The unchanged publisher executes the same atomic lease step with the trial-defined ref; it cannot use or overlap the real-corpus lease ref, and foreign/interrupted trial ownership gets the same refusal/reconciliation behavior. The run manifest supplies the observed consumer publication base and exact synthetic source/mapping/candidate under those constraints. The default policy gate validates this binding plus the separate actual trial authorization before classifying a run as synthetic. A free-form trial label is insufficient: absent/changed definitions, a different repository/base/input bundle or any file/branch/PR/closure effect outside the definition are refused. This is the sole scoped trial eligibility while real-corpus mode stays staged, not permission for real publishing. Test a valid two-repository trial through the ordinary publisher and negative trial-labelled real-corpus attempts.

The synthetic trial source may be prepared in its isolated fixture repository, but that source commit is not the publication checkpoint. Before candidate review, the trial fixture harness maps only the allowed synthetic output into an owned consumer branch based on the selected default commit. Record both repository/commit identities, the exact path mapping, source/output hashes and full resulting consumer diff in the trial manifest. Make the authorized consumer checkpoint after this materialization, then run the independent candidate reviewer against that exact consumer commit and manifest. The publisher pushes that same reviewed checkpoint without rewriting, transplanting, generating or remapping anything afterward; assert both published head and tree equal the reviewed consumer objects. Mapping changes invalidate review. Fixture materialization is explicit trial setup within its allowed namespace, not an alternate publisher or permission to carry private/real documentation into the draft.

Both the dispatch-only trial and eventual scheduled trigger are thin callers of one committed reusable worker workflow, such as `.github/workflows/docs-drift-shared-worker.yml`. Commit that definition with trial setup and bind its exact blob. It owns the install, scanner/worker, independent reviewer and publisher steps, runner, environment and permission requirements; both callers use that same definition. The adoption helper strictly parses both caller definitions and compares all fields, permitting differences only in `on` and the specifically declared literal synthetic-input/output values under `with`. Exact permissions, secret-name mappings (no implicit `secrets: inherit`), environment and invocation must match; an extra step/job/field or unexplained difference denies adoption. The common worker's blob and both callers' compared fields join the trial and adoption bindings. For first adoption these are the trial and scheduled callers; later upgrade trials use the dormant candidate worker and prospective-caller comparison defined below. The dispatch-only workflow must exercise the same install, worker, reviewer and publisher entry points as the eventual scheduled workflow. Record exact workflow/job blobs, consumer commit, installed component digest/source/version, scanner/settings/fixture digests, provider/model identities, native results, reviewed candidate and actual draft-PR observations. Expected differences are limited to trigger, the explicitly bound synthetic input/output namespace and that fixture materialization before the consumer checkpoint. The candidate-review and publication steps themselves are unchanged. For first adoption, a different component, provider/model, permissions, invocation, reviewer or publisher behavior invalidates the trial and requires another trial. Later component changes use the explicitly reviewed upgrade route below; execution/provider/reviewer/permission/publication changes still require a new trial. Static YAML validation and a local interactive model call cannot satisfy this condition. Corpus/scanner parity against the actual current consumer remains separately required; the synthetic trial does not prove real-corpus accuracy.

Cutover evidence is assembled without a self-referencing commit. First prepare an exact consumer source candidate C containing adopted-mode routing/settings, the fixed adoption-record path and all worker/generator inputs, but no new adoption record. Obtain paired source-candidate review at C; a missing adoption record still denies live publication at this stage. Retain its native returned records, the passing unattended advisory trial and the passing installed-model resolve/closure collector trial as immutable artifacts. Operator verification and the pre-cutover attestation must bind both trial results to the exact component before D can be delivered. Then create final cutover child D whose only change from C is the declared adoption-record file. That file refers to C and those already existing trial/review artifacts; it contains neither D's ID nor a post-cutover observation. The adoption helper mechanically verifies D's parent C, the exact record-only diff and every frozen policy/worker/scanner/component binding before the separately authorized merge. Any other D change requires a fresh source-candidate review. This special assembly belongs only to the owner-operated migration; ordinary advisory/resolve/trial publishers still push exactly their independently reviewed commit with no post-review evidence commit.

The first post-cutover runtime gate requires current-default adopted mode, the valid committed pre-cutover attestation with recorded passing advisory and resolve/closure trial outcomes and paired source-candidate acceptance, and matching current protected route/component/policy bindings. It checks the committed fields and bindings, not private historical artifact bytes. It does not require completion state `adopted` or the first scheduled publication to have already happened. After merge, a separate read-only installed-route/corpus/publication-gate check observes the cutover. Its external completion receipt records the actual merged/default revision and those observations; each committed adoption record remains immutable, including when a later upgrade selects a separately named successor record. A separately authorized documentation update can link that receipt later without redefining it or becoming a runtime prerequisite. Later ordinary repository changes use normal assessment freshness; current protected publication/worker inputs must continue to match the adopted record.

Adoption evidence distinguishes `interactive_ready` from external scheduled state `legacy`, `trial-pending`, `trial-failed`, `trial-passed` and `adopted`. The last is a completion observation derived only after the trial, verified D assembly/merge and post-cutover checks; it is never an input required to create itself. If the trial is unavailable, failed or incomplete, keep both legacy publishing routes, retain pending evidence and leave AC-06/full feature completion unchecked. Preserve the old worker as the scoped rollback target. No spending, workflow dispatch, secret transfer or real backlog mutation follows from these evidence states.

Operator verification before D merges must read and hash the original trial, native review and installed-test artifacts, validate their exact targets/model/results, and verify C/D assembly against the source objects. Store a portable attestation in D with artifact hashes, identities and verdicts plus the protected manifest and predecessor linkage, excluding private source/report bodies, credentials and host paths. The hosted runtime gate reads that committed attestation and current Git blobs/selected component, validates the schema, required recorded outcomes/identity/binding consistency and protected inputs, and needs no private `artifact_root`. It trusts the owner-reviewed adoption attestation as such; it cannot independently prove historical model/test execution from a hash alone. Neither an inaccessible local path nor a dead artifact URL becomes a hosted prerequisite. Corrupt/missing committed fields and changed protected bindings still fail closed. This split applies to durable adoption history only: the current prepared candidate's original review/check artifacts remain available to and verified by its publishing wrapper before push. Operator verification cannot be satisfied by runtime-only mode.

### Protected adoption bindings and ordinary scan inputs

The adoption record protects an explicit manifest: shared docs-drift component/version/source and transitive runtime dependencies; reusable-worker blob and effective caller contract (with explicit component-pin selection bound separately); install/worker/reviewer/publisher invocations and provider/requested-reviewer identities; runner, execution environment, job permissions and secret-name mappings; shared scan/protocol validator version plus any separately implemented protocol-translation adapter; and real-corpus routing, publication/closure rules and lease policy. Effective policy fields, rather than the digest of the whole consumer settings file, define these protected bindings. The selected adoption-record path is bound but the record's own digest is not embedded in its inputs. This is a closed manifest: missing/unknown protected fields or uncertain dependency influence cannot establish compatibility.

The ordinary assessment input set includes corpus/source content and history, local detector implementation/rules/options, detector-unit/input selectors, documentation roots/exclusions/suffixes and suppression/correction history. Changes there require a fresh complete scan and candidate evidence/review but no new adoption trial by themselves. They remain consumer-owned. A detector-rule change is not automatically a protocol change. Raw scanner/settings/feedback hashes still bind each assessment; they do not freeze those entire files for the lifetime of adoption. This rule also applies when a scanner emits the protocol directly rather than using a separate adapter. If a change alters the required protocol/translation, worker invocation, decision or effect-authority contract, classify that changed protected behavior through re-adoption instead of disguising it as a detector setting. Missing required execution or an incompatible scanner report still denies readiness through the scan validator.

Dormant upgrade-trial definitions and candidate worker files may be added through separately authorized trial setup without changing the active production manifest. Each trial binds its own exact current-default definition and allowed candidate inputs/effects; additions cannot change the approved production worker, its selected record or real-corpus policy. Changes to normal scan scope/options/feedback and additions to this trial setup are therefore not a reason to invalidate the approved production adoption record. The active manifest excludes unrelated files and unselected dormant candidates, while each actual scan and trial retains its own strict freshness bindings.

### Upgrades after adoption

Keep the approved source/plugin pin and adoption-record selection active while an updater proposes its replacement. An updater PR alone cannot change the running worker. Do not merge a pin bump first and leave the default branch pointing at an unapproved component; assemble and authorize the verified successor together. Interactive runs using an unadopted upgraded component may assess/prepare, but current-default binding checks deny their real-corpus publication. The approved pinned worker continues to operate during that review. No legacy fallback is silently re-enabled.

Classify an upgrade from the full old-to-new shared/consumer diff, including relevant instructions, runtime dependencies and transitive helper inputs; version numbers and release notes alone cannot establish compatibility. A compatible change is a reviewed display-only change or unrelated vh-adlc change that preserves assessment/scan contracts, selected inputs and decisions, worker execution, provider/reviewer identity, permissions, secret exposure, lease behavior and publication/closure semantics. Retain exact old/new component identities, the examined dependency/read set and independent compatibility findings. Unknown influence or incomplete dependency evidence requires the full live trial. The adoption helper checks evidence/binding consistency; this remains owner-reviewed compatibility evidence, not enforced semantic proof.

A compatible pin bump adds the new immutable component pin and changes only the active caller's declared `component_pin` selection plus the adoption-record selection. This mechanical pin selection is the explicit caller-contract exception for compatible re-adoption; pin bytes/new component identity are reviewed and tested separately. The reusable-worker blob, all other caller fields and protected behavior must stay unchanged. Any other worker-blob change is an execution change requiring the trial route. A candidate trial and its prospective scheduled caller select the same candidate pin, so their comparison does not ignore arbitrary extra inputs.

For a compatible upgrade, obtain independent review and actual fresh/upgrade installed-payload checks for the new exact version, plus affected regressions and consumer command/worker contract checks. Prepare source candidate C with the new component pin and a distinct successor-record path while the approved default stays unchanged. Obtain paired source/compatibility acceptance at C, then use the same record-only child D assembly and separately authorized delivery as first adoption. The successor record binds the previous immutable adoption record and its passing trial, exact old/new components, compatibility classification, installed-test artifacts and fresh C review. The gate accepts this explicit compatible-re-adoption chain only when the preserved behavior/policy bindings match and the current component equals the newly reviewed/tested component. It does not pretend the old trial executed the new bytes, or require those bytes to equal the old trial's component. A missing/stale compatibility review or installed check denies the upgrade. Keep prior records; update the selected record path rather than overwriting evidence.

A change to the protected execution/protocol, provider/reviewer, permission/secret, lease or publication/closure behavior requires another separately authorized live unattended trial at the proposed version, followed by C review, record-only D assembly and post-update observations. Local detector rules, ordinary scan scope/options and feedback remain normal assessment inputs as listed above. To run that upgrade trial while production remains approved, separately authorize a default-branch setup that adds a distinct dormant candidate reusable-worker file and a dispatch-only caller. The current-default trial definition binds their exact blobs, proposed component/provider/permissions, allowed synthetic namespace and the intended prospective scheduled-caller contract. The active scheduled caller still references the old approved worker and record; it does not share the candidate file yet. The bounded synthetic trial may load only that explicitly named candidate, even though it differs from the active production binding, and cannot publish real-corpus findings. During this interval compare the trial caller to the prospective scheduled-caller contract, not the still-active old caller. After the trial, source candidate C switches the scheduled caller to that exact tested candidate worker; mechanically require its normalized caller fields and all protected candidate bindings to match the passing trial. D adds only the new immutable record. An unexpected candidate ref/blob, permission, invocation or caller difference requires re-review/retrial. Test a permission- or execution-changing candidate trial passing while the old approved scheduled worker continues to pass its production gate. The same conservative path applies when compatibility is uncertain. A failed/unavailable upgrade trial leaves the approved default pin/record active. Neither classification grants automatic merge, publication, paid execution or secret transfer. After an authorized upgrade, recheck installed routing and gate behavior at the observed default. Rollback selects the prior approved pin, record and matching migration-owned inputs together; preserve unrelated newer work and refuse mismatched combinations.

First adoption and the upgrade verification suite must exercise both supported surfaces. Before first cutover, and again when resolve publication or superseded closure changes, run a bounded actual model resolve trial using the exact installed candidate and synthetic proposal/diff/feedback/merge histories through a hermetic remote collector. It must observe consolidation publication, denial before merge, verified post-merge explanation/closure, and abandonment/revert refusal; assert the exact attempted effects and that no real backlog IDs can enter the namespace. The actual model executes the installed resolve procedure; the tracker transport and merge event are fixtures, so report this as a model/collector trial rather than a real GitHub merge/closure. This supplements the separately authorized unattended advisory trial required by the settled upgrade policy; advisory success alone cannot verify a changed resolver. Lease/advisory changes must likewise exercise the corresponding contention/publication path. A missing affected-surface trial leaves the upgrade unverified even when its other trial passes.
