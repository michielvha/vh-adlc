FINDING: F-01
KIND: judgement
SEVERITY: should-fix
WHERE: Design; Scope; Acceptance Criteria (AC-01); Test Plan (AC-01 row); Open Questions
EVIDENCE: Design (docs/specs/feature.md:30) says only "If the POST fails, notify.sh exits 1 and the build is marked unreported." It never says whether notify.sh retries, how often, with what backoff or timeout, or whether a later rerun of notify.sh for the same build is allowed. It also leaves partial failure open: a timeout after the server already accepted the POST gives exit 1 and "unreported" while the server holds the result, and any retry or rerun then sends a second POST for the same build, which breaks "one POST per build" (Scope, docs/specs/feature.md:26) and "one POST with its build ID" (AC-01, docs/specs/feature.md:34). Nothing says whether the status API deduplicates on build ID. One implementer will build no retry and another will build retries, and only one of them meets AC-01 under a transient failure. Under the no-retry reading, any transient network error loses that build's report for good, which works against the Owner summary's "Report each build result" (docs/specs/feature.md:18).
PROPOSAL: Define the retry policy (count, timeout, backoff) and the replay rule: either the POST is idempotent on build ID and the API ignores duplicates, or retries and reruns are forbidden. Add a criterion and a Test Plan row for a stub that fails or times out once, then check the resulting POST count and exit status. Because the document settles a trade-off here, raise the choice as an Open Question.

FINDING: F-02
KIND: judgement
SEVERITY: blocking
WHERE: Frontmatter goal; title line (docs/specs/feature.md:12); Context, Owner summary; Scope; Design; Acceptance Criteria (AC-01); Test Plan (AC-01 row)
EVIDENCE: The goal is "notify.sh posts a build result to a remote status API" (docs/specs/feature.md:5, repeated at :12), and the Owner summary says "Report each build result to the status service" (:18). Design says the POST carries only "the build ID" (:30), with no result field. AC-01 covers only "A successful build" (:34), and the Test Plan checks only that a POST arrives with the build ID (:40). With every box ticked, a failed build may send nothing, and no POST says whether the build passed or failed. So the stated problem, reporting the build result, is not solved.
PROPOSAL: Put the result (for example pass or fail) in the request body in Design, and add criteria and Test Plan rows covering both a successful and a failed build, each checking for exactly one POST with the build ID and the correct result.

FINDING: F-04
KIND: factual
SEVERITY: should-fix
WHERE: Design
EVIDENCE: Design (docs/specs/feature.md:30) says "Builds never overlap, a lock file in /run serializes notify.sh runs, so concurrent requests cannot happen." No citation is given for "Builds never overlap". notify.sh at f1ed76c is "#!/bin/sh" then "true" (notify.sh:1-2), so it takes no lock, and nothing else in the tree (AGENTS.md, notify.sh, the document) creates one. If the lock is meant to be built, Scope, the criteria, the Test Plan and Tasks never mention it. The two halves also conflict: if builds never overlap, a lock is not needed, and if a lock is needed, overlap is possible. The lock's partial failure path is undefined too: a notify.sh run that crashes or is killed leaves the lock file behind, and the document does not say whether the next run waits forever, fails, or removes a stale lock. It also does not say what happens when the lock is busy.
PROPOSAL: Either cite evidence that builds cannot overlap and drop the lock, or make the lock part of scope with its path, its wait or fail behaviour, and stale lock recovery, plus a criterion and a Test Plan row that run two notify.sh invocations at once and one that starts with a leftover lock file.
