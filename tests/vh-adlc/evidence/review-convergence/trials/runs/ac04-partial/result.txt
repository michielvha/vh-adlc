FINDING: F-01
KIND: factual
SEVERITY: should-fix
WHERE: Design
EVIDENCE: Design says "Both files keep the previous version's plain-text format, so upgrade and rollback need no migration." release.sh:1-2 is only `#!/bin/sh` and `echo "$1"`. The tree holds only AGENTS.md, release.sh and docs/specs/feature.md, so neither releases.log nor latest.txt exists and no previous format can be kept. The document never defines the format either: one version per line or not, trailing newline or not, and where the files live (the working directory, the script directory or a fixed path).
PROPOSAL: Remove the claim about a previous format. Define the new format and the file locations: one version and a newline per releases.log line, latest.txt holding exactly the version and a newline, both paths relative to a named directory. Say what rollback to the old release.sh leaves behind.

FINDING: F-02
KIND: judgement
SEVERITY: should-fix
WHERE: Design
EVIDENCE: Design says "Only one release.sh runs at a time, guarded by flock." It does not name the lock file, whether a second run waits or fails at once, any timeout, or its exit status and message. flock is a util-linux command (/usr/bin/flock here) that /bin/sh hosts such as macOS do not ship by default, and the document does not say whether that dependency is acceptable.
PROPOSAL: Name the lock file path and state whether a second concurrent run blocks or exits non-zero with a message. State that flock is a required dependency, or choose a portable lock and justify it.

FINDING: F-03
KIND: judgement
SEVERITY: should-fix
WHERE: Design
EVIDENCE: Design says "A failed append is retried once" and then "overwrites latest.txt". It leaves these cases undefined: the retry also fails (exit status, whether latest.txt is still written); the append succeeds but the latest.txt overwrite fails, so the two ledgers disagree; an in-place overwrite is interrupted and leaves latest.txt truncated; a retry after a partial append writes the version twice; and running release.sh again with the same version (replay) appends a duplicate. A missing or empty version argument is also undefined, since release.sh:2 echoes "$1" unchecked.
PROPOSAL: Define the failure contract. A failed retry exits non-zero and leaves latest.txt untouched. latest.txt is replaced atomically through a temp file and rename. State whether a repeated version is rejected, skipped or appended, and what happens with no argument.

FINDING: F-04
KIND: judgement
SEVERITY: should-fix
WHERE: Acceptance Criteria, Test Plan
EVIDENCE: AC-01 "After a release, releases.log ends with the version and latest.txt holds it." Test Plan row AC-01 "Run release.sh 1.2.0 and read both files". With every box ticked, an implementation without flock, without the retry, with a non-atomic overwrite, or that replaces releases.log instead of appending still passes. The proof also passes without a new append if releases.log already ended with 1.2.0. It gives no starting state and no pass condition beyond reading the files.
PROPOSAL: Add criteria and Test Plan rows for appending to existing history (seed releases.log with 1.1.0, then expect both lines in order), for concurrent runs, for a failed append after one retry, and for a failed latest.txt write. Give each row a starting state and an exact pass condition.
