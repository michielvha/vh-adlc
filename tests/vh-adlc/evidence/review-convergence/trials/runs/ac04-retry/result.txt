FINDING: F-01
KIND: judgement
SEVERITY: should-fix
WHERE: Design; Open Questions
EVIDENCE: Design says "If the POST fails, notify.sh exits 1 and the build is marked unreported." The document does not say whether notify.sh or the build system retries, how many times, or with what backoff. It also does not define the case where the POST reaches the server but the response is lost or times out. In that case the build is marked unreported even though the status was recorded, and a rerun of notify.sh sends a second POST. That breaks Scope "one POST per build" and AC-01 "one POST". Open Questions says "None." even though no retry is a trade-off the document settles.
PROPOSAL: Define the retry and replay behaviour: retry count, which failures are retried, and whether the POST carries an idempotency key, or the build ID used as one, so a replay does not create a duplicate status. Raise the retry choice as an Open Question for the owner instead of settling it silently.

FINDING: F-02
KIND: factual
SEVERITY: should-fix
WHERE: Context, Background; Design
EVIDENCE: Background cites notify.sh:1 for "notify.sh runs once per build; the status API is a remote HTTPS service". notify.sh:1 is `#!/bin/sh` and notify.sh:2 is `true`. Neither line supports either claim. Design also says "Builds never overlap" with no citation. This uncited claim is the basis for "concurrent requests cannot happen".
PROPOSAL: Cite the build configuration or a command output showing that notify.sh runs once per build and that builds never overlap, and name the status API endpoint source. Otherwise restate these as assumptions and raise them as Open Questions.

FINDING: F-03
KIND: factual
SEVERITY: should-fix
WHERE: Design; Acceptance Criteria; Test Plan
EVIDENCE: Design says "a lock file in /run serializes notify.sh runs". No lock exists in the tree (notify.sh:1-2 is only `#!/bin/sh` and `true`). The document does not say whether the lock is existing behaviour or something to build. No criterion or Test Plan row covers it. It does not define the lock path, whether a second run waits or fails, or what happens to a stale lock left by a crashed or killed run. A stale lock would block every later notification. Design also says builds never overlap, which makes the lock's purpose unclear.
PROPOSAL: State whether the lock is to be built. If it is, specify its path, the behaviour on contention and the recovery from a stale lock, and add a criterion and a Test Plan row for it. If it is not needed, remove it and rely on the cited no-overlap fact.

FINDING: F-04
KIND: judgement
SEVERITY: should-fix
WHERE: Design; Acceptance Criteria; frontmatter goal
EVIDENCE: The goal is "notify.sh posts a build result to a remote status API". Design says the POST carries "the build ID" and does not say it carries the result. AC-01 covers only "A successful build produces one POST with its build ID". The Test Plan row checks only "exactly one POST with the build ID". With every box ticked, a POST that has a build ID but no pass or fail result passes. Failed builds are never reported, so the stated problem remains.
PROPOSAL: Specify the request body, including the result field, and cover both successful and failed builds in the criteria. Make the Test Plan stub check that the posted result matches the build outcome for each case.

FINDING: F-05
KIND: factual
SEVERITY: should-fix
WHERE: Design
EVIDENCE: Design says "The request body keeps the previous version's fields, so upgrade and rollback need no migration." The tree has no previous version that sends any request (notify.sh:2 is `true`), and the document names no fields. The upgrade and rollback claim rests on a body that does not exist and is not specified.
PROPOSAL: Name the exact body fields and their source. If this is the first version, say there is no previous format, and define what rollback to the current no-op script means for builds already reported.

FINDING: F-06
KIND: judgement
SEVERITY: should-fix
WHERE: Design; Acceptance Criteria; Test Plan
EVIDENCE: Design defines a failure path ("exits 1 and the build is marked unreported"), but no criterion or Test Plan row checks it. The document does not say what marks the build unreported or where that mark is stored. notify.sh exiting 1 marks nothing by itself. A proof covering only AC-01 passes an implementation that exits 0 on failure or never records the unreported state.
PROPOSAL: Name the component and the store that record "unreported", and add a criterion and a Test Plan row in which the stub server returns an error and the check observes exit status 1 and the unreported mark.

FINDING: F-07
KIND: judgement
SEVERITY: should-fix
WHERE: Test Plan; Design
EVIDENCE: The AC-01 proof is "A stub server records exactly one POST with the build ID". The Design does not say how notify.sh gets its endpoint URL or credentials. Without a configurable endpoint, the test cannot point notify.sh at a stub. Two implementers would choose different configuration mechanisms, such as an environment variable, an argument or a hard-coded URL.
PROPOSAL: Specify how the endpoint URL and any authentication reach notify.sh, and write the Test Plan row as an executable procedure that uses that mechanism with a pass condition.

KIND: judgement
SEVERITY: should-fix
WHERE: Context, Owner summary
EVIDENCE: The whole Owner summary is "Report each build result to the status service." It leaves out the failure behaviour (exit 1, unreported), the absence of retry, the lock file, the upgrade and rollback claim, the out of scope item and the validation state (no proof has been observed).
