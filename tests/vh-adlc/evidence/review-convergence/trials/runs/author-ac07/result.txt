## Design paragraphs, quoted

**Concurrent requests**
> `deploy.sh` has no lock today (`deploy.sh:1-2`) and this feature adds none. When two deploys run at the same time, on one host or several, each run posts its own message once its own `./ship-release` returns. The chat service orders them by arrival, which can differ from the order the deploys finished. Each message carries the revision, host and UTC finish time, so a reader can tell the two apart and see which finished last. The notify step shares no file or state between runs, so concurrent runs cannot corrupt each other's message.

**Partial failure**
> The deploy and the notification are separate steps with no transaction between them, and the deploy always comes first. The cases are:
> - Deploy succeeded, post failed (DNS, TLS, refused connection, non-2xx, timeout): the deploy stands, the script exits 0, and stderr carries the failure line. The channel shows nothing for that deploy.
> - Deploy succeeded, post timed out after the service accepted it: the channel shows the message while stderr reports a failure. The script cannot tell this case from a lost request.
> - Deploy failed: the script still posts the failure message (Q1) and exits with the deploy's code.
> - `deploy.sh` is killed during the post: the deploy has already finished; the message may or may not arrive. The 10 second limit (Q3) bounds how long a hung webhook can hold the script.

**Retry and replay**
> The draft makes one attempt and does not retry (Q4). A retry after a timeout could post the same message twice, because the generic webhook takes no idempotency key and the case above shows a timed-out request may already have landed. Re-running `deploy.sh` by hand, for the same or another revision, is a new deploy and sends a new message; the team may see two messages for one revision, each with its own time. There is no stored "already notified" state to replay from or to deduplicate against.

**Upgrade and rollback**
> The feature adds no stored state, schema or file outside `deploy.sh`, so neither direction needs a migration.
> - Upgrade on a host without `DEPLOY_CHAT_WEBHOOK_URL`: deploys behave as before plus one warning line on stderr and no post. Setting the variable turns the post on with no code change.
> - Rolling back `deploy.sh` to the previous version: deploys stop posting. A variable left set is ignored. Nothing needs cleaning up.
> - Deploying an older application revision with the new `deploy.sh`: the message names whatever revision `git rev-parse` reports in the working tree, so a rollback deploy shows up in chat like any other.
> - Removing the webhook on the chat side: posts fail with a non-2xx response, which the partial failure rules above already cover; deploys keep working.

## Open Questions that cover these cases, quoted

> ### Q2: Should a failed notification ever change deploy.sh's exit status?
> **Recommendation:** A. Never; a deploy that worked should not be reported as failed because chat was down.
>
> | Option | You get | It costs |
> | --- | --- | --- |
> | **A. Never** | Deploy pipelines see only the deploy's result | A broken webhook can go unnoticed except for a stderr line |
> | **B. Fail on notify error** | Broken notifications get noticed at once | A chat outage makes successful deploys look failed and may trigger rollbacks or retries |
>
> **Why this is yours:** It trades notification reliability against deploy pipeline behaviour.

> ### Q3: How long should deploy.sh wait for the webhook?
> **Recommendation:** A. 10 seconds, which covers a slow TLS handshake without stalling a pipeline for long.
>
> | Option | You get | It costs |
> | --- | --- | --- |
> | **A. 10 seconds** | A bounded wait; AC-04 tests it | A very slow but working service may be cut off |
> | **B. 30 seconds** | Fewer false timeouts | A hung webhook holds every deploy up to half a minute |
>
> **Why this is yours:** The right bound depends on how the team runs deploys and how much delay it accepts.

> ### Q4: Should deploy.sh retry a failed post?
> **Recommendation:** A. No retry; a timed-out post may already have landed, and a retry would then duplicate it.
>
> | Option | You get | It costs |
> | --- | --- | --- |
> | **A. One attempt** | At most one message per deploy | Brief outages drop the message |
> | **B. One retry after 2 seconds, only on connection errors and 5xx** | Survives brief blips | Up to 22 seconds of waiting; a 5xx after delivery can still duplicate |
>
> **Why this is yours:** It chooses between missed and duplicated messages.

> ### Q6: Should a missing webhook URL be a silent skip, a warning, or an error?
> **Recommendation:** A. Warn on stderr and skip, so hosts without the variable keep deploying.
>
> | Option | You get | It costs |
> | --- | --- | --- |
> | **A. Warn and skip** | Safe rollout host by host | A host missing the variable stays quiet in chat until someone reads the log |
> | **B. Fail the deploy** | No host can deploy unannounced | Every host must have the secret before the next deploy |
>
> **Why this is yours:** It decides rollout order and whether notification is mandatory.

## Summary
- **What it does:** after `./ship-release` finishes, `deploy.sh` makes one HTTPS POST to the URL in `DEPLOY_CHAT_WEBHOOK_URL`. The message gives the result, the revision, the host and the UTC time. The URL never appears in arguments or output, and the script always exits with the deploy's own code.
- **Out of scope:** changes to `ship-release`, locking against concurrent deploys, other channels, and setting up or rotating the webhook secret.
- **Tests:** a shell test against stub `ship-release` and `curl` commands, needing no network, plus one manual post to a real test channel. These are planned only; nothing has been run.
