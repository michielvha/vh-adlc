FINDING: F-01
KIND: factual
SEVERITY: blocking
WHERE: Test Plan, AC-01 row; Design
EVIDENCE: Design gives `docs(readme): fix a link` as a correct subject. The AC-01 proof pattern is `^[a-z]+: .+$`. Running `printf '%s\n' 'docs(readme): fix a link' | grep -Eq '^[a-z]+: .+$'` printed nomatch, so the proof rejects a subject the Design calls correct. The row has passed review: R-1 at `0b58093` already held this row's text (`git diff 0b58093 76c7f6d` changes only the Review Log) and returned NO FINDINGS. This finding still counts as blocking because it shows the pattern rejecting correct output, not just widening it.
PROPOSAL: Let the pattern accept an optional parenthesised scope after the type, for example `^[a-z]+(\([a-z0-9-]+\))?: .+$`. Add `docs(readme): fix a link` to the row's must-pass examples.

FINDING: F-02
KIND: judgement
SEVERITY: should-fix
WHERE: Design; Acceptance Criteria, AC-01; Open Questions
EVIDENCE: Design says "A correct subject starts with a type, a colon and a space". That rule leaves out the scope form `docs(readme):` that its own example uses. It also leaves out the trailing period rule that its wrong example `fix: handle empty input.` relies on. Nowhere does the document say which types are allowed, whether any lowercase word counts, or whether there is a length limit. AC-01 says only "accepts correct subjects and rejects wrong ones", so two implementers could reasonably build different rule sets. Open Questions says "None." even though the allowed type set is still undecided.
PROPOSAL: State the full subject rule in Design: type set, optional scope, no trailing period, and any length limit. Make AC-01 name those rules. Raise the type set (a fixed list or any lowercase word) as an Open Question for the owner.

FINDING: F-03
KIND: judgement
SEVERITY: should-fix
WHERE: Design; Test Plan, AC-01 row
EVIDENCE: The document never says how lint-msg.sh receives the subject (argument, stdin, or a commit message file path as in a commit-msg hook), and it never says what accept and reject look like (exit status, output). The proof says "lint-msg.sh matches the subject against `^[a-z]+: .+$`". That describes how the script is built, not a check someone can run. The standard asks for a test, a scenario with a pass condition, or a written manual procedure. With the current script (`lint-msg.sh:2` is `exit 0`), nobody can say how to run this proof.
PROPOSAL: Define the input and the exit codes in Design. Rewrite the proof as a scenario, for example: run `sh lint-msg.sh "<subject>"` on each example and expect exit 0 for every must-pass example and a non-zero exit for every must-fail example.
