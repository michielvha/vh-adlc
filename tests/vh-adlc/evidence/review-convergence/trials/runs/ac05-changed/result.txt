FINDING: F-01
KIND: factual
SEVERITY: blocking
WHERE: Test Plan (AC-01 row); Design
EVIDENCE: Design calls `docs(readme): fix a link` a correct subject. The AC-01 proof pattern `^[a-z]+: [a-z].*$` rejects it: `printf '%s\n' 'docs(readme): fix a link' | grep -Eq '^[a-z]+: [a-z].*$'` fails. The row has not passed review. R-1 reviewed 101303a, and dd5e32b changed the row from `^[a-z]+: .+$` to `^[a-z]+: [a-z].*$` after that. The previous pattern also rejected this subject, so the defect predates that change and the change did not fix it.
PROPOSAL: Allow an optional parenthesised scope after the type, for example `^[a-z]+(\([a-z0-9-]+\))?: `, and add `docs(readme): fix a link` to the row's must-pass examples.

FINDING: F-02
KIND: factual
SEVERITY: blocking
WHERE: Test Plan (AC-01 row); Design
EVIDENCE: Design defines a correct subject only as one that "starts with a type, a colon and a space" and does not end with a period. `fix: Handle empty input` meets that definition, but `grep -Eq '^[a-z]+: [a-z].*$'` rejects it. The previous revision (dd5e32b, "fixture: change the pattern row") added this rejection when it replaced `.+` with `[a-z].*`. Design never says the description must start in lower case.
PROPOSAL: Either state in Design that the description must start with a lower case letter, raised as an Open Question because it is a format trade-off, or return the description part of the pattern to one that accepts any first character.

FINDING: F-03
KIND: factual
SEVERITY: should-fix
WHERE: Test Plan (AC-01 row); Design
EVIDENCE: Design calls `fix: handle empty input.` a wrong subject because it ends with a period. The pattern accepts it: `printf '%s\n' 'fix: handle empty input.' | grep -Eq '^[a-z]+: [a-z].*$'` succeeds. The row's must-fail examples list only `handle empty input`. So the proof passes an implementation that accepts trailing periods. This is not a nit, because the row changed in dd5e32b after R-1 reviewed 101303a and so has not passed review.
PROPOSAL: End the pattern with `[^.]$` or something equivalent, and add `fix: handle empty input.` to the row's must-fail examples.

FINDING: F-04
KIND: judgement
SEVERITY: should-fix
WHERE: Acceptance Criteria (AC-01); Design; Open Questions
EVIDENCE: AC-01 reads "lint-msg.sh accepts correct subjects and rejects wrong ones." It does not define correct or wrong. Design gives examples but does not settle which types are allowed (any lower case word, or a fixed list such as fix, docs, feat), the syntax of the scope, what characters the description may use, or the maximum length. Open Questions says "None." The standard says every trade-off the document settles must be raised as an open question.
PROPOSAL: Define the subject grammar in Design (allowed types, scope syntax, description rules) and refer to it from AC-01. Raise the choice between a fixed type list and any lower case word as an Open Question.

FINDING: F-05
KIND: judgement
SEVERITY: should-fix
WHERE: Design; Test Plan (AC-01 row); Context (Owner summary)
EVIDENCE: Design does not say how lint-msg.sh gets the subject (argument, file path or stdin), which exit codes mean accept and reject, or what it prints. It also does not say how the script is invoked. The Owner summary says "Check commit subjects before a push", but Scope and Design never mention a push hook or any trigger. `ls -l lint-msg.sh` shows `-rw-r--r--`, so the script is not executable today. The proof "lint-msg.sh matches the subject against ..." describes how the script is built, not a check anyone can run. It names no command and no pass condition, such as an exit status for each example.
PROPOSAL: Specify the interface and the trigger in Design, for example "reads the subject as $1, exits 0 to accept and 1 to reject, run from a pre-push hook" or drop the push claim. Rewrite the proof as a runnable check, for example a test script that runs lint-msg.sh on each must-pass and must-fail example and checks the exit codes.
