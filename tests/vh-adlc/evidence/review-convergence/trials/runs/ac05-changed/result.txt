FINDING: F-01
KIND: factual
SEVERITY: blocking
WHERE: Test Plan, row AC-01; Design; Acceptance Criteria, AC-01
EVIDENCE: Design calls `docs(readme): fix a link` a correct subject. The AC-01 row pattern `^[a-z]+: [a-z].*$` rejects it: `printf '%s\n' 'docs(readme): fix a link' | grep -Eq '^[a-z]+: [a-z].*$'` returned no match. The proof therefore fails a correct implementation. Commit 3a2f640 changed this row after R-1 (from `^[a-z]+: .+$` to `^[a-z]+: [a-z].*$`), so the row has not passed review at its current text. The earlier pattern also rejected the scoped form, so the defect predates that change and survived it.
PROPOSAL: Allow an optional parenthesised scope after the type, for example `^[a-z]+(\([a-z0-9-]+\))?: `, and add `docs(readme): fix a link` to the row's must-pass examples.

FINDING: F-02
KIND: factual
SEVERITY: should-fix
WHERE: Test Plan, row AC-01; Design; Acceptance Criteria, AC-01
EVIDENCE: Design calls `fix: handle empty input.` a wrong subject because it ends with a period. The AC-01 row pattern accepts it: `grep -Eq '^[a-z]+: [a-z].*$'` matched `fix: handle empty input.`. The row's must-fail list holds only `handle empty input`, so an implementation that accepts a trailing period passes the proof. The row text changed in 3a2f640 after R-1's clean pass at 0b58093, so the nit rule for a free-text pattern row that has passed review does not apply.
PROPOSAL: Make the pattern reject a trailing period, for example by ending it with `[^.]$`, and add `fix: handle empty input.` to the must-fail examples.

FINDING: F-03
KIND: judgement
SEVERITY: should-fix
WHERE: Design; Acceptance Criteria, AC-01; Test Plan, row AC-01; frontmatter goal
EVIDENCE: The goal says "the team's format", AC-01 says "correct subjects" and "wrong ones", and Design defines the format only through examples. Several rules are left open: whether the type must come from a fixed list (feat, fix, docs and so on), whether the description must start in lowercase (the row pattern requires `[a-z]` after the space, but Design never says so), whether there is a length limit, and whether `!` breaking-change markers are allowed. AC-01 bundles accepting and rejecting into one composite criterion that defers to this unstated definition.
PROPOSAL: State the full subject rule in Design, including the type set, scope, case, trailing punctuation and any length limit, and make the Test Plan pattern and examples cover each rule. Raise any of these choices that is a trade-off as an Open Question.

FINDING: F-04
KIND: judgement
SEVERITY: should-fix
WHERE: Design; Test Plan, row AC-01
EVIDENCE: Design says "lint-msg.sh checks a commit subject" but does not say how the script receives the subject (argument, stdin, or a commit message file path as a `commit-msg` hook gets), how it takes the subject from a multi-line message, or what it signals on failure (exit code, message). The AC-01 proof, "lint-msg.sh matches the subject against" a pattern, describes code internals rather than a check someone can run. lint-msg.sh is currently `#!/bin/sh` / `exit 0` (lint-msg.sh:1-2), so the tree defines no interface either.
PROPOSAL: Define the input, how the first line is extracted, and the exit status for accept and reject in Design. Rewrite the proof as a runnable scenario that calls lint-msg.sh with each example and checks the exit status.
