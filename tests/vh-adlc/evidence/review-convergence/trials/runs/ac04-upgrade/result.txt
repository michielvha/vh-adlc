FINDING: F-03
KIND: judgement
SEVERITY: should-fix
WHERE: Design (flock sentence); Acceptance Criteria; Test Plan
EVIDENCE: Design says "Only one cache.sh runs at a time, guarded by flock" but leaves out four things. It does not name the lock file. It does not say whether a second run blocks, waits with a timeout, or fails. It does not say whether the lock covers the whole read, compute, merge and write cycle. It does not say what happens when a lock holder hangs. If the lock is taken on state.json itself, the rename swaps in a new inode, so two runs can hold locks on different files and both write, and one run's new key is lost. No criterion or Test Plan row covers concurrent runs.
PROPOSAL: Name a lock file that is never renamed (for example state.json.lock). State that the lock is held from reading state.json until after the rename, and give the behaviour of a second run. Add a criterion with a proof in which two runs with different inputs start together and both keys end up in state.json.

FINDING: F-04
KIND: judgement
SEVERITY: should-fix
WHERE: Design (write, rename and retry sentences); Acceptance Criteria; Test Plan
EVIDENCE: Design says "A failed rename is retried once" but never says what happens when the retry also fails. The exit status, whether the computed result is still printed, and whether state.json.tmp is removed or left are all undefined. It also never covers a state.json.tmp left by an earlier crash. The crash claim "a crash leaves the last complete file" has no criterion and no Test Plan row, so an implementation that writes state.json in place passes AC-01.
PROPOSAL: Define the outcome when both rename attempts fail: exit status, output, and temp file cleanup. Define how a leftover state.json.tmp is handled. Add a criterion and proof for crash safety, for example killing the run between the temp write and the rename and checking that state.json still parses and still holds the earlier keys.

FINDING: F-05
KIND: judgement
SEVERITY: should-fix
WHERE: Design (first sentence)
EVIDENCE: "writes results to state.json as a new JSON object keyed by input hash" leaves several things open. The hash algorithm is not given, and neither is the hashed input (only `$1`, or the input file contents when `$1` is a path). The stored value is not given either: stdout, the exit status, or both. Nor is it said whether a failed `compute` (non-zero exit) gets cached. Where state.json lives (current directory, next to the script, or a configured path) is not stated. Two implementers would build caches that differ in hits, location and stored content.
PROPOSAL: Specify the key (algorithm and exact hashed input), the stored value, the rule for failed computes, and the state.json path.

FINDING: F-06

EVIDENCE: The Design defines no behaviour for a missing state.json, which is the first run after upgrading from today's cache.sh (cache.sh:1-2 keeps no state).
