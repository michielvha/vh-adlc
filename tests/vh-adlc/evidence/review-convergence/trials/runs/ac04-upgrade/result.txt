FINDING: F-01
KIND: judgement
SEVERITY: should-fix
WHERE: Design; Scope; Context (Owner summary)
EVIDENCE: Design line 30 says "cache.sh writes results to state.json as a new JSON object keyed by input hash" but gives the object no format version. It also does not say what a run does when state.json already exists and cannot be parsed or has another shape, or when it was written by a newer or older cache.sh. Today's script keeps no state at all (cache.sh:1-2), so this release is the first version that writes state.json. The document never defines what happens on the upgrade (the first run with no file, or a stray file of the same name), on rollback (old cache.sh ignores the file, which leaves stale entries that a later upgrade would trust), or on a future format change. Scope line 26 rules out only expiry.
PROPOSAL: Add a format version field to state.json. Define what happens when the file is missing, unparseable or carries an unknown version (for example: treat it as empty, recompute and rewrite). State what rollback to the stateless script leaves behind and whether re-upgrading trusts those entries. Then add a criterion and a Test Plan row for the unreadable or old-format case.

FINDING: F-02
KIND: judgement
SEVERITY: should-fix
WHERE: Design
EVIDENCE: Design line 30: "A failed rename is retried once." Nothing says what happens when the retry also fails: the exit status, whether the computed result is still printed, and whether state.json.tmp is removed or left in place. It also does not say what a later run does when it finds a state.json.tmp left by a crash, or whether a result is cached when compute exits non-zero (cache.sh:2 runs `compute "$1"` without checking its status).
PROPOSAL: Define the outcome after the second rename fails (exit code, output, temp file cleanup), how a run treats a leftover state.json.tmp, and that a failed compute is not cached. Cover at least the failed compute case with a criterion.

FINDING: F-03
KIND: judgement
SEVERITY: should-fix
WHERE: Design
EVIDENCE: Design line 30: "Only one cache.sh runs at a time, guarded by flock." It does not name the lock file, and it does not say whether a second concurrent run waits, times out or exits, or with what status. If the lock is taken on state.json itself, the rename that replaces state.json breaks the lock: a waiting run then locks the old inode while a third run locks the new one. flock(1) is also not POSIX, and cache.sh is `#!/bin/sh` (cache.sh:1).
PROPOSAL: Name a dedicated lock file that is separate from state.json and is never renamed. State whether contention blocks or fails and the resulting exit status, and name flock as a required dependency.

FINDING: F-04
KIND: judgement
SEVERITY: should-fix
WHERE: Design; Acceptance Criteria (AC-01)
EVIDENCE: Design line 30 keys entries by "input hash" but names neither the hash function nor what the input is: only `$1`, or `$1` plus the compute version. It also does not say where state.json lives (the working directory, the script directory or a state directory), and it gives no JSON tool for a sh script. Two implementers would write caches that disagree on keys and location, and AC-01's "reads its result from state.json" could refer to different files.
PROPOSAL: Specify the key derivation (the hash tool and exactly what is hashed), the path of state.json (and state.json.tmp on the same filesystem), and the JSON tool the script depends on.

FINDING: F-05
KIND: factual
SEVERITY: should-fix
WHERE: Test Plan (AC-01 row); Acceptance Criteria (AC-01)
EVIDENCE: Test Plan line 40: "Run cache.sh twice with one input and see the second run skip the computation". It names no way to observe the skip, such as a stub `compute` that counts its calls, and no pass condition on output. AC-01 line 34 only requires that the second run "reads its result from state.json". It does not require the second run to print the same result as the first. An implementation that reads the file but prints nothing or a wrong value would pass both.
PROPOSAL: Restate AC-01 as the end state: a second run with the same input prints the same result as the first without invoking compute. Make the proof a scripted check with a stub compute on PATH that records each call. The check passes when the call count is 1 after two runs and the outputs are byte-identical.
